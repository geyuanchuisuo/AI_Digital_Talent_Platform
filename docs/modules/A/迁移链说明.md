# 迁移链 · 运行说明（G1 公共前置，2026-11-07 建立）

> 维护：A；命名约定依据 U-05 裁决。本目录配合 `alembic.ini`（backend/ 下）使用，
> 连接串一律取自本人 `backend/.env`，不落 Git。

## 命名与链

- `A_*.py`：公共 / 招聘表变更（A 维护）
- `C_*.py`：测评 / 面试 / 培训表变更（C 提交，A 只负责链上衔接）
- `B_*.py` / `D_*.py`：B、D 落地表变更时各自提交
- 现行链：`A_0001_baseline`（公共 13 表）→ `C_0001_c_module`（C 域 21 表）→ …
- 每个迁移只做一件事；`downgrade` 必须可回滚；表结构以 `app/models` 为准，
  改模型必须同步新增迁移 + `backend/tests/test_models_structure.py` 对照清单。

## 三类场景

| 场景 | 操作 |
|---|---|
| **全新空库** | `python scripts/init_db.py`（create_all 建全部 34 表 + seed，并自动 `alembic stamp head`）；或 `alembic upgrade head` 从零建表后手工 seed |
| **已有旧 13 表库**（2026-11-07 前 init_db 建的库，无 C 表） | 先 `alembic stamp A_0001_baseline`（13 表即基线态），再 `alembic upgrade head` 建 C 的 21 表。⚠️ 不要直接跑 init_db：它只 create_all 不 ALTER，stamp head 会跳过 C 迁移 |
| **已是 34 表库** | 直接 `alembic upgrade head` 走增量 |

命令均在 `backend/` 下用 venv 解释器执行：`./.venv/Scripts/python.exe -m alembic <cmd>`。

## 与 init_db 的关系（双轨）

- `init_db.py` 继续负责**空库快速初始化**（建库、create_all 全部表、seed），建表成功后
  自动 `alembic stamp head`，让 alembic 状态与新库一致；
- `alembic` 负责**已有库的增量演进**（加列、加索引、改类型）——`create_all` 不 ALTER，
  任何已有库的表结构变更都必须走迁移，禁止只改模型不写迁移。

## 已知约定差异（待收敛）

- C 域 21 表 `updated_at` 由应用层维护（`CTimestampMixin`，无 `ON UPDATE CURRENT_TIMESTAMP`），
  公共 13 表由 MySQL 维护（`UpdatedAtMixin`）；对齐请求已发 C，收敛前两类表并存，
  `test_models_structure.py` 按各自口径断言。
