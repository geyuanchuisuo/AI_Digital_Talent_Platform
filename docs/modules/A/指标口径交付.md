# A 域指标口径交付（T-A53，供 D 的白名单指标问数核对）

> 版本：v0.1　|　日期：2026-11-07　|　维护：A　|　消费者：D（白名单指标问数）
> 依据：tasks/A.md「向 D 提供岗位需求、人工推进、缺口和匹配复核指标的时间、状态、去重与允许维度」；字段以 master 实际模型为准（`backend/app/models/job.py`），表结构变更走迁移链（当前 head `A_0004_merge_heads`）。

## 0. 通用口径

| 项 | 口径 |
|---|---|
| 时间字段 | 全部为**本地时间 Asia/Shanghai**（T-16 口径；`created_at`/`updated_at` 由 MySQL 维护，`*_at` 业务时间戳由应用写入） |
| 去重键 | 结果表唯一键见 §3/§4；同一 `(批次, 人才)` 只有一行（retry 补缺不重跑，D-E） |
| 权限范围 | 读取走 `AccountScope`（`backend/app/core/auth/scope.py`）：管理侧 `can_view_all_persons=True` 可全量；个人侧仅本人 `person_id`。**D 的问数服务端必须先过滤再聚合**，不得只靠前端 |
| 软删除 | `talent_profiles.deleted_at IS NOT NULL` 的主档：结果行保留（历史可追溯），但**统计「有效候选人」时排除** |
| 硬淘汰 | `hard_fail=1` 的行 score=0（匹配）或 NULL（筛选置底），聚合平均分时应排除或单独分组 |

## 1. 岗位需求（job_profiles）

| 维度 | 字段/口径 |
|---|---|
| 岗位标识 | `id`（主键）、`title`、`department`、`version`（同一 title 多版本并存，统计按 `id` 不按 title） |
| 状态 | `is_active`（1=启用）——**活跃岗位数** = `is_active=1 AND 按 title 去重取最新 version` |
| 时间 | `created_at`（建岗时间）、`updated_at`（最近变更；版本变更不改旧行，新建行） |
| 允许维度 | 按 `department`、按 `created_at` 时间窗、按 `is_active` |
| ⚠️ 待补 | 「需求人数 headcount」字段属 M3 人才需求实体（V2.5 冻结后建表），当前无此列——缺口指标见 §5 |

## 2. 筛选（screen_batches / screen_results）

| 维度 | 字段/口径 |
|---|---|
| 批次 | `screen_batches`：`id`、`job_profile_id`+`job_profile_version`（快照绑定）、`status`（pending/running/done/failed）、`total`（快照人数）、`progress`、`passed`/`pending_count`/`rejected`（done 时按结果表重算）、`started_at`、`finished_at`、`retry_count`、`vector_degraded` |
| 结果行 | `screen_results`：唯一键 `uk_screen_batch_talent (screen_batch_id, talent_profile_id)`；`hard_fail`/`hard_fail_reason`；`score`（硬淘汰 NULL）；`verdict`（自动三档）/`manual_verdict`（人工三态）/`manual_verdict_by`/`manual_verdict_at`；**有效结论 = `COALESCE(manual_verdict, verdict)`**（人工优先，H-A06 口径） |
| 版本追溯 | `model_version` / `prompt_version` / `attempt` / `profile_input_snapshot_json`（2026-11-07 功能 5b 起） |
| 允许维度 | 按批次、按岗位（batch 的 job_profile_id）、按有效结论、按时间窗（started_at/finished_at）、按 model_version |
| 去重注意 | 批次按岗位版本隔离——同岗位重新筛选 = 新批次新快照，**跨批次聚合按 talent_profile_id 去重时须取最新批次**（口径由 D 的指标定义层决定，A 提供数据不提供去重策略） |

## 3. 匹配（match_batches / match_results）

| 维度 | 字段/口径 |
|---|---|
| 批次 | `match_batches`：同 screen 结构，另有 `hard_failed` 计数；无三档计数列（匹配是排名语义） |
| 结果行 | `match_results`：唯一键 `uk_match_batch_talent`；`score`（硬淘汰=0 置底）、`dimension_scores_json`（含 `vector_similarity` 键，降级为 null）、`reason`（评分依据，功能 5a 起内容有据） |
| 人工标记 | `manual_verdict`（passed/pending/rejected，**人工推进标记**，T-A41）/`manual_verdict_by`/`manual_verdict_at`——**人工采纳率** = manual_verdict 非空行中 passed 占比（口径示例，最终定义归 D） |
| 版本追溯 | 同 §2 四字段 |
| 名次 | **不持久化**（`rank` 查询时按 score 排序计算，模型注释 D-8）——D 问数如需名次请按 `score DESC, id ASC` 自行窗口计算 |
| 允许维度 | 按批次/岗位/时间窗/人工标记/硬淘汰分组 |

## 4. 人工推进链（招聘视角）

| 指标 | 数据来源 | 口径 |
|---|---|---|
| 初筛人工介入率 | screen_results | `manual_verdict IS NOT NULL` 占比 |
| 匹配人工采纳率 | match_results | manual_verdict=passed 占比 |
| 改判时间 | manual_verdict_at | 本地时间 |
| 操作人维度 | manual_verdict_by | users.id（可 join `users.username`/`display_name`） |

⚠️ 「邀请→面试→录用」推进指标属 M3 招聘状态/邀约记录（未建表）；C 的面试轮次（`interview_rounds`）为 C 域数据，D 可直接读 C 表但不属本交付。

|---|---|
| 需求人数 / 人工推进人数 / 剩余需求 | **M3 人才需求实体未建**（V2.5 冻结后落地），当前无数据来源 |
| 五阶段对外映射统计 | V2.5 §16 待冻结（内部标记→对外阶段映射边界未定稿） |

## 6. D 消费方式建议

1. **直接读表聚合**（推荐）：D 在白名单内按上述字段写只读 SQL（PgSQL 只读副本同步后）；避免经 API 逐条拉取。
2. **不读的字段**：`profile_input_snapshot_json`（大 JSON，含候选人输入原文——指标聚合不需要，且按 AccountScope 属敏感面）。
3. 变更通知：A 域表结构变更走迁移链并在 `docs/updates/A/` 登记；D 的指标 SQL 若引用新列请以本文档 + 迁移记录为准。
