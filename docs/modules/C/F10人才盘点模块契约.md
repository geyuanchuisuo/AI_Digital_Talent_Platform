# F10 人才盘点模块接口与数据契约（一期）

> 状态：设计稿，待 ownership 登记 `inventory` 后由 C 实现代码。
> 依据：用户需求文档 §F10、细化 v1 D-28/29/30/32、REQ-INV-001~004、2026-11-07 六组裁决第 5 项。
> 归属：C（见 `docs/requests/C/20261107-A-F10人才盘点归属登记.md`）。
> 本文只描述 C 侧契约；组织范围/部门经理数据范围由 A 的授权服务判定，C 不自行实现组织树。

## 1. 范围与边界

纳入一期：能力评估（五档）、绩效×潜力九宫格、人才池、个人发展计划、经理初评/HR 确认、员工异议、匿名汇总与导出审计。

不做：自动晋升/调薪/淘汰、AI 自动评级、视频面评、与绩效系统自动联动。

数据来源（只读，不修改他方表）：
- 测评能力：`assessment_results`（员工 purpose，已评分最新版本）。
- 培训成长：`training_growth_events` / 学习记录。
- 绩效、自评、经理评价、岗位技能、工作/项目经历：一期无对应业务表，由盘点模块自带录入字段承载（见 §2），不伪造来源。

## 2. 数据表（6 张，均无外键，JSON 快照版本化）

复用 C 的 `CTimestampMixin`。`employee_id` 即服务端用户 id（员工）。

### inventory_assessments（盘点评估主表，一员工一当前版本链）
- `employee_id`、`period_label`（如 `2026`）、`rating_five`（五档，确认前可空）
- `performance_level`（high/medium/low，无正式绩效则空）、`potential_level`（high/medium/low，HR 确认前空）
- `grid_cell`（九宫格 1-9，绩效或潜力缺失/未确认则空，表示待评估）
- `status`：`draft`(经理初评) / `pending_hr` / `confirmed` / `returned`
- `manager_id`、`manager_comment`、`hr_id`、`hr_comment`、`confirmed_at`
- `version`、`supersedes_id`（版本链）、`source_snapshot_json`（测评/培训等输入快照）

### inventory_potential_reviews（经理潜力初评，REQ-INV-002）
- `assessment_id`、`dimension_scores_json`（学习敏捷/适应变化/承担复杂职责/跨团队影响力）
- `rationale`（必填依据）、`status`(pending/confirmed/returned)、`reviewer_hr_id`、`hr_note`

### inventory_pools（人才池配置，HR 维护）
- `name`、`criteria_json`（准入/退出标准）、`status`(active/inactive)、`approved_by`

### inventory_pool_members（人才池进出记录，HR 确认生效）
- `pool_id`、`employee_id`、`action`(join/exit)、`reason`、`suggested_by`(经理)、`confirmed_by`(HR)、`status`(pending/confirmed/rejected)
- 唯一约束：`(pool_id, employee_id, status=pending)` 防重复建议（用部分唯一或应用层校验）。

### inventory_development_plans（个人发展计划 IDP）
- `employee_id`、`assessment_id`（可追溯关联）、`title`、`goal`、`actions_json`(行动/责任人/期限/进展)
- `status`(active/done)、`review_note`(复盘)、`created_by`

### inventory_objections（员工异议/补充）
- `employee_id`、`target_type`(assessment/feedback/plan)、`target_id`、`content`
- `status`(submitted/reviewing/resolved)、`manager_note`、`hr_note`、`resolved_at`

另：导出与匿名汇总不建表，走 §4 实时计算 + `inventory_audit_events`（可复用 C 事件风格，记录 actor/action/scope/at）。

| 五档评级 | 不可见 | 读本部门当前 | 读写 | 读写 |
| 九宫格位置 | 不可见 | 读本部门当前 | 读全量 | 读全量 |
| 人才池归属/类别 | 不可见 | 读类别+进出原因 | 读写 | 读写 |

## 4. 路由（`/api/inventory`，全部走统一响应与错误体）

管理/HR/经理：
- `POST /assessments` 创建/发起盘点评估（经理或 HR）
- `GET /assessments` 列表（按角色裁剪：经理仅本部门当前，HR 全量）
- `GET /assessments/{id}` 详情（按 §3 裁剪字段）
- `POST /assessments/{id}/potential-review` 经理提交潜力初评（必填 rationale）
- `POST /assessments/{id}/hr-confirm` HR 确认/退回（confirm|return，必填 note）
- `GET /grid?period=` 九宫格分布（仅 HR/经理；样本<5 的统计项隐藏）
- `GET /export/summary?scope=dept` 部门匿名汇总导出（样本<5 隐藏；审计）
- `GET /export/detail?employee_ids=` HR/管理员个人明细导出（审计）

人才池：
- `POST /pools` /`PATCH /pools/{id}` HR 配置池
- `POST /pools/{id}/suggest` 经理建议 join/exit（幂等：同人同池 pending 唯一）
- `POST /pool-members/{id}/confirm` HR 确认/驳回

员工侧：
- `GET /my/assessment` 本人可见视图（无评级/九宫格/池）
- `POST /objections` 提交异议（target 限本人可见对象）
- `GET /my/plans` / `POST /plans` / `PATCH /plans/{id}` 发展计划（员工+经理协作）

## 5. 关键规则

1. **待评估**：绩效或潜力任一缺失/未确认 → `grid_cell` 空、不进入九宫格，不推断填补（REQ-INV-002 AC-1）。
2. **确认链**：经理初评(status=draft→pending_hr) → HR confirm/return；确认后写 `rating_five`、`potential_level`、`grid_cell`、`confirmed_at`，生成新版本，`supersedes_id` 指旧版。退回则 `returned` 保留原因。
3. **五档/阈值**：五档名称、绩效口径、九宫格轴阈值/象限命名由 HR 配置（存 `inventory_pools` 之外的配置项或 `sys_settings`，一期用 `sys_settings` 键 `inventory.config`），未配置不产出正式评级（REQ-INV-002 阻塞项）。
4. **九宫格计算**：`grid_cell = f(performance_level, potential_level)`，3×3 映射；纯函数，可单测。
5. **匿名汇总**：任一统计维度样本 <5 → 该项不返回（D-30）。
6. **导出审计**：每次导出写审计事件（导出人、范围、时间、类型）。
7. **异议**：不改变正式结果；HR 确认更新时生成新版本，原记录保留（REQ-INV-004 AC-3）。
8. **幂等**：池建议同人同池 pending 唯一；评估创建按 `(employee_id, period_label)` 幂等。

## 6. 与 C 已有模块的关系

## 10. 实现更新（C09，2026-11-11）：九宫格阈值与配置版本机制

本节记录实际落地的实现，覆盖 §5 规则 3/4 与 §4 路由中关于阈值来源的描述。数据表以已发布代码为准（复核主表 `inventory_reviews`，非本文初稿的 `inventory_assessments`）。

- **阈值不硬编码**：绩效×潜力九宫格的“高/中/低”分档来自经 HR 批准的配置版本表 `inventory_grid_configs`，不再使用代码内固定阈值。每版本含 `performance_bands_json`{hi_min,mid_min}、`potential_bands_json`{hi_min,mid_min}、可选 `job_family`、`labels_json`、`note`，状态 `draft`→`approved`；校验 `1 ≤ mid_min < hi_min ≤ 5`。
- **产出规则**：`grid_cell(score)` 仅在存在 `approved` 配置版本且绩效、HR 潜力齐备时产出正式档位（缺档为“待评估”，`grid_cell` 空）；无批准版本时确认动作明确报错，不产出评级、不推断填补。
- **版本可追溯**：`inventory_reviews.grid_config_version` 记录确认当时依据的配置版本；历史复核不因新标准重算（迁移 `C_0008_grid_config`）。草稿/提交阶段用当前生效配置产出“临时”档位，正式档位以 HR 确认为准。
- **路由**（`/api/inventory`，管理/HR）：`POST /grid-configs` 新建草稿、`POST /grid-configs/{id}/approve` 批准生效、`GET /grid-configs` 版本列表（按版本倒序）。对应事件 `grid_config_created`/`grid_config_approved`。
- **待确认阈值数值**：具体 hi_min/mid_min 数值仍属 HR 决策项（§9），机制交付不等于批准数值；测试以显式夹具给定分档，不代表业务已批准。

## 11. 实现更新（C09 深度收口，2026-11-11，MASTER 集成）：经理本人初评与负责范围授权

本节记录经理初评与数据范围的实际落地，覆盖 §3 权限矩阵与 §4 路由中「部门经理被统一管理门禁拒绝」「填经理分即视为初评」的旧实现偏差。数据表以已发布代码为准（`inventory_reviews`）。

- **经理本人初评入口**：`POST /reviews/{id}/manager-assessment`（body `potential_manager_score` 1–5 + 可选 `comment`）。仅 `MANAGER` 角色（A06 `viewer_tier`）、仅负责部门员工、仅 `draft` 阶段可调用；`reviewer_manager_id` 强制记为初评经理本人，写 `manager_comment`（迁移 `C_0011` 新增列）与 `manager_initial_reviewed` 事件。已提交/确认的复核拒绝修改，须走新版本复核。
- **代填不计初评**：`submit_review`/`confirm_review` 强制 `potential_manager_score` 与 `reviewer_manager_id` 同时非空——管理侧通过 `create`/`update` 代填经理分不会设置 `reviewer_manager_id`，因此不能替代经理本人初评；缺初评时提交/确认返回 400。
- **负责范围授权**：`create_review`/`list_reviews` 经 A06 `resolve_data_scope`/`get_visible_department_ids` 判定——管理侧按 scope（all/dept）、部门经理仅本部门（`require_employee_in_scope`，员工无部门或不在可见部门集→403）、员工仅本人。部门经理不再被 `_require_admin` 统一门禁拒绝发起/查看本部门盘点；`update`/`submit`/`confirm`/人才池/汇总/配置仍限管理侧。
- **F10 内部评级隔离**：员工视角 `list_reviews` 不返回 `grid_cell` 与内部评分（绩效/经理潜力/HR 潜力/九宫格），与 C13 成长轨迹员工视角隐藏 `hr_ability`/正式评级维度一致。
- **验证边界**：`tests/C` 新增经理初评本人留痕、管理侧代填不计、非经理角色 403、跨部门经理 403 等反例（SQLite + X-Test-User 替身身份）；真实 JWT/MySQL/浏览器联调未验证。前端 `/inventory` 新增「经理初评」tab（仅 `dept_manager`），沿用既有 `isManager` 模式，仅类型/单测验证。
