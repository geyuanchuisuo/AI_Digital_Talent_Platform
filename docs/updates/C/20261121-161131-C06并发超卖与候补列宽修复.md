## 一、根因与修复

### C06-A 并发报名超卖

- 根因：`apply_enrollment` 先对课程行 `SELECT ... FOR UPDATE` 串行化，但随后 `_occupying_count` / `_reserved_awaiting_count` 是普通一致性读。请求鉴权阶段已对 `users` 做过一致性读，REPEATABLE READ 读视图在等待课程行锁前建立；等待结束后计数仍读旧快照，两个请求都得到 0。
- 修复：两处容量统计改为对同课程报名行 `SELECT id ... FOR UPDATE` 当前读（SQLite 自动忽略，行为不变），课程行锁 + 当前读共同保证后到请求看到前一请求已提交的占位/预留。
- 同时收紧相关并发点：候补选取改为当前读，避免并发取消已提交后被旧快照选回；`release-expired` 先按课程 ID 升序锁课程行，再逐行 `FOR UPDATE` 复核状态/期限，避免扫描后状态被并发确认/审批改变时按旧快照覆盖；释放统计改为实际复核成功数。

### C06-B 候补递补 500

- 根因：`TrainingEnrollment.status` 为 `String(20)`，`awaiting_confirmation` 为 21 字符；MySQL 严格模式拒绝写入，SQLite 不校验长度故单测未暴露。
- 修复：模型列宽改为 `String(32)`；迁移 `C_0012_enroll_status` 将存量列 `VARCHAR(20)` 幂等加宽到 `VARCHAR(32)`，保留 `NOT NULL DEFAULT 'pending'`。降级前检查是否存在超过 20 字符的状态，存在则拒绝降级，防止截断。
