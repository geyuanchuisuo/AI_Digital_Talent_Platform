## 三、C06 失败项（本轮新发现的真实缺陷，未修复）

**C06-A（严重）并发报名容量不变量失效（真实 MySQL）**

- 课程容量 1、免审批；两名员工同时 `POST /api/training/enrollments`，三次复验均得到 `approved + approved`（期望 `approved + waitlisted`）。聚焦复验记录：`{"statuses":["approved","approved"],"invariant_ok":false}`，DB 两行均为 approved。
- 根因分析：`apply_enrollment` 用课程行 `SELECT ... FOR UPDATE` 串行化，但随后的 `_occupying_count` 是普通一致读；在 MySQL 默认 REPEATABLE READ 下，读视图由请求早期（鉴权查询 users）建立，等待行锁期间看不到前一请求提交的新报名，导致两请求都读到 0 并同时通过。修复方向：占用计数改为当前读（如对同课程报名行加锁读取/原子座位计数）或将相关事务隔离级别调整为 READ COMMITTED，并补真实 MySQL 并发回归测试。

**C06-B（严重）候补递补在 MySQL 直接 500**

- `POST /api/training/enrollments/release-expired` 触发 `_promote_waitlist` 时抛 `DataError (1406): Data too long for column 'status'`：模型 `TrainingEnrollment.status` 为 `String(20)`，而状态值 `awaiting_confirmation` 为 21 字符。SQLite 测试不校验长度，故单测未暴露。
- 影响：候补超时释放→通知下一位→本人确认的整条链在真实 MySQL 不可用；复验中确认接口随后返回 400「当前状态不可确认候补名额」。修复需加宽列（迁移）并补 MySQL 回归用例。

**已通过的 C06 语义（同一轮）**：顺序报名可正确形成 `pending + waitlisted`；候补管理员直接审批返回 400「该报名已处理」；候补在递补前本人确认返回 400「当前状态不可确认候补名额」——「候选不可绕过递补」成立。
