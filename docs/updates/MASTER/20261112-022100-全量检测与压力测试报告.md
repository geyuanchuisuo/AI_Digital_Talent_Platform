## 三、压力测试结果（本机实测，非验收口径）

- **环境**：本机 Windows，uvicorn `--workers 1`（127.0.0.1:8000），MySQL 8 容器（3307/`ai_talent_yb`），Milvus 2.6.24 容器，httpx/asyncio 客户端同机注入；代码基线 `3ab27fe`；2026-11-12 02:03–02:16。原 PRD §7 验收目标（并发≥2000、普通接口≤1s 等）需独立负载环境与口径，本数据仅描述本机容量与韧性，**不作为达标或不达标验收结论**。

| 阶段 | 负载 | 结果 |
| --- | --- | --- |
| P0 串行基线 | /api/health ×30 串行 | p50 48ms / p95 95ms，全 200 |
| P1 无鉴权突发 | /api/health c=150 ×450 | **450/450 全 200**，但 p50 2.85s / p95 4.95s / rps≈49——事件循环饱和，无错误 |
| P2 登录 | c=20 ×120 | 全 200；p50 661ms / p95 1452ms / rps≈25（bcrypt 密集） |
| P3 单端点突发 | 5 个鉴权读端点各 c=100 ×100 | 基本全 200（仅 admin-overview 2 个客户端协议异常）；p50 0.76–1.21s、p95 1.01–1.99s、rps 44–94 |
| P4 持续混合 | 5 端点轮换 c=60 ×1200 | **386 成功 / 812 客户端超时(15s) / p50 15.0s / rps 5.6**；服务端 **451 个 500**，全部为 `QueuePool limit of size 10 overflow 20 reached, connection timed out, timeout 30.00`（池 30 连接 + anyio 线程池默认 40 双层耗尽） |
| P4 后探活 | GET /api/health | **无响应（服务楔死）**，与此前客户端中断在途请求后的楔死现象一致，重启才恢复 |

- **韧性发现（本轮最重要）**：持续负载超过服务容量时，系统无请求级超时、无背压、无快速失败——客户端超时断开后，服务端线程仍占住池连接不可中断（`run_in_threadpool` 内 DB 等待），僵尸请求级联占满 30 连接与 40 线程，health 一并失守，**唯一恢复手段是重启进程**。单端点短突发（P3）表现尚可、持续混合负载（P4）即崩溃，容量上限实测在 c≈40–60 之间。
- **对照原 PRD §7 目标的差距**（差距陈述，非验收）：并发≥2000 与实测可承载 c≈40–60 差 2 个数量级以上；普通接口≤1s 在突发下 p95 已达 1.0–2.0s，持续负载下完全失守。页面渲染/向量检索/缓存命中/可用率等其余指标本轮未测。
- **修复方向建议**（供负责人评估，未动代码）：请求级超时与取消传导、池等待快速失败（缩小 pool_timeout 并返回 503/429 而非 500）、DB 依赖端点异步化或线程池扩容、在 D02 限流/黑名单启用态下做保护性限流、Redis/PG 路径独立验收。
