## 一、口径核实（先确认跑的是对的东西）

`docs/modules/MASTER/20261109-执行跟踪表核验.md` 对 A03 写的是「整项 × 撤回」——核实后明确：这是把**已实现标记撤回到未实现**（× 的粒度收窄），并拆出 A15「执行时输入留存」，**不是撤销 A03 需求**。原执行表 A03 通过条件仍为：

> 批次开始绑定 B 正式版本/内容，排队期间修改档案不影响本批；重试和历史回读不读取新版本。

B 契约 §6 阶段 2 承诺「版本表落地后按版本回读」；本轮实测 `talent_profile_versions` 表已存在（隔离库 1564 行历史版本）、`history.save_version` 在 `api/talents.py` / `profile_service.py` / `talent_service.py` / `dedup_service.py` 多处生产接线，故 A03 可以真正绑定 B 正式版本，而非只做 A 侧快照兜底。

## 二、逐条比对后定位的真实缺口

既有已具备：成员名单 `resolved_ids` 快照、岗位配置 + 模型/Prompt 版本快照（T-A42）、结果级 `profile_input_snapshot_json`（A15 口径，执行时写）、retry 只补缺、请求级幂等。

但两个 worker（`screen_worker.py` / `match_worker.py`）在**执行时**才读 `talent_profiles` + 最新 `parsed_resumes.structured_json` 拼 `profile_input`。因此：

1. 批次创建到执行之间（排队期）发生人工修订 / 重新解析 / 字段变更，会**回溯改变本批评分依据**；
2. retry 补缺的成员会读到**新版本档案**，与同批已写成员口径不一致；
3. 历史回读虽能看结果行快照，但**批次层面没有「开始时绑定的 B 正式版本/内容」**，无法核对本批到底基于哪一版档案。

T-A42 冻结的是**岗位配置**与模型版本，不是成员档案内容；A08 冻结的是**申请输入**，两者都不覆盖 A03。

## 四、设计取舍（明确写下来，避免后续误改）

- **批次级冻结，不是只存版本号**：只存 `(person_id, version)` 仍需在执行时读 B 表，历史版本一旦被清理即失效；值拷贝让排队期变更、retry、历史回读全部自包含。
- **绑定 B 正式版本但不改写 A 侧评分口径**：B 契约 §5 承诺「A 现有 `profile_input` 键不变，只追加新键」。本轮以 A 侧等价值拷贝作评分输入，B 持久化快照作为**可核对的内容绑定**（版本号 + 内容 sha256 + 子集），不把 B 快照里脱敏的 `name` / 结构不同的 `tags` 直接灌进 Prompt，避免评分语义漂移。
- **只冻结内容、不冻结存在性**：T-24 既有「批次创建后软删画像 → 跳过并计 `skipped_deleted`」语义保留；worker 仍查当前档案判断软删/不存在，但不取其字段值。
- **`config_snapshot_json` 不被污染**：引擎按白名单把它当岗位入参拼 Prompt C，成员冻结数据单独放 `frozen_inputs_json`，不混入。
- **幂等 replay 不重新冻结**：T-A42 命中同键返回原批次，沿用原 `captured_at`；「岗位/档案变更新建一轮」仍成立（换键或不传键）。
- **详情只回摘要**：`frozen_inputs` 给 `available/schema/frozen_count/captured_at/version_sources`，不回 `items` / `profile_input`（与 `resolved_ids` 不外泄同口径）。
- **没有 B 版本行的历史数据**：`a_baseline` 兜底并仍冻结 A 侧值拷贝，不阻断创建。
