## 一、逐条比对后定位的真实缺口

既有代码并非空白：`applications` 已有 `job_profile_version`、`resume_file_id`、`internal_stage/external_stage` 五阶段映射、终态结果类别与 HR 确认；`interview_rounds` / `ai_interview_sessions` 已由 C 侧建立指向 `applications.id` 的外键。真正缺的是：

1. **申请输入只有引用、没有值拷贝**。`create_application` 仅存 id/version，岗位条件、JD、人才档案、简历解析结果后续被 UPDATE 后，历史申请回看时无法复现当时的评分依据，违反 §73 / §201 / §280。
2. **个人端列表存在越权与字段泄露**。`GET /api/recruitment/applications` 未做数据范围过滤，仅靠前端传 `talent_profile_id`，后端并未以 `AccountScope` 收窄——伪造参数即可读他人申请；且 `_application_out` 把 `internal_stage`、`stage_reason`、`stage_updated_by`、`result_confirmed_by`、`job_profile_version`、`resume_file_id` 等内部字段一并返回。
3. **未确认的终态结果提前外露**。阶段推进到终态即写入 `result_category=hired/not_hired`，接口未做发布过滤；需求要求「终态及最终结果须 HR 确认后才发布」。

### 快照结构（`schema_version = A08-v1`）

`captured_at`、申请时 `job_profile_version`、实际用于快照的 `resume_file_id`，以及 `job_profile` / `jd_publication` / `talent_profile` / `resume_file` / `parsed_resume` 五段值拷贝和 `missing_sources`。

设计取舍：

- **值拷贝而非引用**：按字段白名单复制，源行后续 UPDATE 不反映到快照。Decimal→float、datetime/date→ISO，保证 JSON 列可落库。
- **原文不整段复制**：`parsed_resumes.raw_text` 是 MEDIUMTEXT，改用 `raw_text_sha256` + `raw_text_length` 固定可核对性；评分真正使用的 `structured_json` 完整冻结，原件由 `resume_file.file_hash` 追溯。
- **缺源容错**：历史/演示数据可能只有 id 没有实体行，缺失项写入 `missing_sources` 并置 None，**不阻断创建**（既有 `test_recruitment_api.py` 用 `job_id=1 / talent_id=398` 仍可创建）。
- **未指定原件时回退**到该档案最近一条 `parsed_resumes`，仅用于快照，不改申请行的 `resume_file_id`。
- 年龄/性别等受保护属性只在**评分时**排除（T-A34），快照忠实记录历史输入，不代表参与评分。
- **面试/邀约引用不重复冻结**：由 C 归属 `interview_rounds.application_id` 等外键承载，A 不越界改 C 文件；执行表 A08 的「完整面试/邀约引用」属跨角色联调，登记为边界而非本单元交付。

### 个人侧获准字段（`_application_public_out`）

仅 `id`、`job_profile_id`、`external_stage`、`result_category`、`result_published`、`stage_updated_at`。`result_category` 只在 `result_published=True` 时返回真实值，未确认前为 `None`；内部阶段、推进原因/操作人、岗位版本、简历原件 id、快照内容一律不返回。完整快照只经管理侧角色门禁接口读取；迁移前历史行返回 `available=false / snapshot=null`，不报错。

## 三、本轮两个环境陷阱（务必记住）

1. **`alembic_version.version_num` 是 VARCHAR(32)**。最初用的 revision id `A_0011_application_input_snapshot`（36 字符）让 MySQL 报 `DataError 1406 Data too long for column 'version_num'`：MySQL 非事务 DDL 已把两列加上，但版本号仍停在 `A_0010`，形成「半迁移」。改为短 id **`A_0011_app_snapshot`** 后重跑，Inspector 跳过已存在的列、版本号写入成功，`current` = `A_0011_app_snapshot (head)`。**今后新增迁移 revision id 必须 ≤32 字符**；迁移文件头部已写入该警示。
2. **迁移 docstring 里误插一组 `"""`** 会提前闭合文档字符串，使后续说明文字变成裸代码，`alembic` 加载时抛 `SyntaxError: invalid character '§'`。已重写文件头部（同时把 `§` 改为 `section`）。教训：给迁移文件补 NOTE 时不要把三引号插在 docstring 中间。

另：首次 `alembic upgrade head` 用了 `| tail` 取退出码，拿到的是 tail 的 0，掩盖了真实失败；已按纪律改为「重定向日志 + 单独 `echo $?`」，`upgrade-exit=0` / `current-exit=0` 为真实值。
