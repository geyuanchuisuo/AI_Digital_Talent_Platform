# A06-2 用户 department_id + 部门行级过滤（接 A06-1 角色门禁 / A06-4 路由）

- 模块：A（系统管理域）
- 执行表：A06 第 2 子单元（P0）
- 提交（待推送后填真实号）：本地 `feature/A/continuation` ahead 1（基于 `78d946e`）
- 关联：A06-1（角色/职责门禁，已发布 `2eca164`）、A06-4（系统管理域 CRUD 路由，已发布 `78d946e`）

## 一、背景

A06-4 已把系统管理域 CRUD 路由挂到 `require_roles("system_admin")` 并写入六张 sys_* 表，但
**`users` 表仍无 `department_id` 列**——因此「部门行级过滤」无法落地：dept_manager 即便被识别为
管理侧职责，也无处挂载「只看本部门」的数据范围。A06-1 的 `data_scope`（all/dept/self）只定义在
`sys_roles` 上，尚无把账号 `data_scope` 解析为「可看哪些部门」并叠加到查询的机制。

本单元补齐 `users.department_id` 列 + 数据范围解析 + 首个部门行级过滤落地（账号花名册），
并把该机制做成下游（B/C/D）可直接复用的基础。

## 二、交付内容

### 修改 `backend/app/models/user.py`
`User` 新增 `department_id: Mapped[int | None]`（`PK_TYPE` 即 BIGINT UNSIGNED，可空）。
无物理外键——与 `system/models.py` 约定一致（一致性由 service 层保证）。

### 新增迁移 `backend/migrations/versions/A_0009_users_department_id.py`
`down_revision = "D_0012_digital_employee"`（统一链当前 head）。幂等：用 `Inspector` 检查
`users` 是否已含 `department_id`，缺才 `op.add_column`（BIGINT UNSIGNED 可空）。空库由
`create_all` 直接获得该列，旧库经本 ALTER 补齐，两条路径同链可用。迁移链 head → `A_0009`。

### 修改 `backend/app/core/auth/scope.py`
- `resolve_data_scope(db, user) -> "all"|"dept"|"self"`：聚合账号所有启用角色的 `data_scope`，
  取「最宽松」口径（任一 all→all；否则任一 dept→dept；否则 self）；无 `sys_user_roles` 绑定时
  回退 `users.role` 简值（hr→all，其余→self）。这是部门行级过滤与下游数据范围的权威来源。
- `get_visible_department_ids(db, user) -> tuple[int,...]|None`：`all`/`self` 返回 `None`（不限制/
  由调用方做本人行级判定）；`dept` 返回 `(users.department_id,) ∪ 跨部门授权(user_scope_grants)`
  去重闭集。
- `apply_department_filter(stmt, model, visible_dept_ids)`：对查询叠加 `department_id IN (...)`
  过滤；`None` 原样返回；模型无该列时防御性返回原 stmt。

### 新增 `backend/app/modules/system/account_router.py`（`prefix=/api/system/accounts`）
- `GET ""`（账号花名册）接 `require_roles("system_admin", "dept_manager")`：system_admin 看全部；
  dept_manager 仅看本部门（含跨部门授权，走 `apply_department_filter`）；支持 `keyword` 模糊过滤。
- `PUT "/{user_id}/department"`（部门指派）仅 `require_roles("system_admin")`：校验部门存在（无 FK，
  service 层一致性），改 `users.department_id`，落 `sys_operation_logs`（F09）。
- 响应经 `_row_to_dict` 序列化并**剔除 `password_hash`**，不泄露凭证。

### 修改 `backend/app/main.py`
新增 `app.include_router(account_router)`，`include_router` 计数 **18 → 19**。

### 修改 `backend/tests/test_models_structure.py`
`EXPECTED_COLUMNS["users"]` 增加 `department_id`（模型与数据库设计列清单对齐，修复 A06-2 引入后
的 schema 断言失败）。该文件归 A。

### 新增 `backend/tests/test_a06_department_scope.py`（UNASSIGNED → 走 `collab.integration`）
11 例：数据范围解析（system_admin=all/dept_manager=dept/legacy hr=all）、账号花名册门禁
（401/403）、system_admin 看全量、dept_manager 仅看本部门、dept_manager 不可改部门（403）、
system_admin 改部门后 dept_manager 立即可见、未知部门 400、未知用户 404。临时账号/部门 teardown 直连清理。

## 三、设计取舍

- **部门行级落地在 A 自有「账号花名册」而非人才/员工数据**：人才主档与员工数据属 B/D 归属，
  A 不触碰；本单元在 A 拥有且能验证的账号管理面证明机制，并把 `resolve_data_scope` /
  `get_visible_department_ids` / `apply_department_filter` 做成下游可复用基础（B/C/D 的人才/
  员工查询只需注入同一套即可获得本部门过滤）。
- **部门指派仅 system_admin**：dept_manager 只读本部门、不可改他人部门，避免权限膨胀。
- **不新建部门种子**：init_db 的部门由真实业务（A06-4 的部门 CRUD）创建；本单元不改 seed，保持
  范围聚焦；`department_id` 无 FK，不强制与 `sys_departments` 行存在性绑定（一致性由 service 层）。
