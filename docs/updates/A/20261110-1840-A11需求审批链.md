### 状态机（审批状态与业务生命周期分离）

```
draft ──submit──> pending ──approve──> approved ──内容变更──> draft(版本+1)
  ↑                  │  └──reject──> rejected ──submit──> pending
  └────return────────┘  └──withdraw──> withdrawn（终态，不可再提交/审批）
```

- **提交**：仅 `system_admin` / `hr`；必填 `position_name` + `headcount≥1` + 合法 `priority` + 至少一个组织/岗位锚点（`project_id` / `project_group_id` / `job_profile_id`）；`pending` 重复提交 409、`approved` 不可重复提交、`withdrawn` 400。
- **审批**：仅 `dept_manager`（业务负责人）/ `system_admin`；仅 `pending` 可决定，非 pending 一律 409（含**重复批准**）；`reject` / `return` 必填原因；**四眼原则按用户 id**（本版本提交人不可自批，同角色不同账号可批）。
- **撤回**：发起方职责，必填原因；撤回后终态。
- **版本冻结**：审批记录记 `demand_version` 与 `A11-v1` 值拷贝快照（当时批的是哪一版、哪些字段）。审批通过后改内容 → `approval_version + 1`、回 `draft`、清 `approved_by/at`、追加 `revision` 记录，`approved_version` 保留为「最后获批版本」；只推进业务 `status`（open→in_progress）**不触发**版本失效。
- **可匹配**：`demand_is_matchable()` = `approved` 且 `approved_version == approval_version`，以 `matchable` 出参暴露；审批状态不可经 `PATCH` 伪造（`extra="forbid"`）。

### 设计取舍

- **不把审批塞进 `status`**：需求 §202 明确业务审批状态不得与技术任务状态混用；`status` 是招聘推进生命周期，审批是业务决策，两套流转互不替代。
- **审批记录只追加**：无 PATCH/DELETE 端点，快照是值拷贝而非引用；`actor_roles` 记录决策时刻的生效角色，便于事后追责。
- **`dept_manager` 映射「业务负责人」**：六类角色里无独立「业务负责人」代码，`system_admin` 作受控兜底但受四眼约束；`hr` 不能审批、`employee`/`candidate` 不能审批/提交。
- **没有把 `matchable` 接成硬拦截**：执行表 A11 的边界是「审批链本身 + 反例」；匹配侧目前按 `job_profile` 而非 `project_demand` 圈人，强行接线会越出 A11 范围并牵动 A05/A09，故只交付可判定字段与服务层纯函数，供后续联动消费，**不宣称已接入匹配入口**。
- **新表而非 JSON 列**：审批记录是审计对象，独立表才能做「只追加、按需求/版本/时间检索、不被业务编辑覆盖」；缺冻结列的历史行由 `approval_status='draft'` / `approval_version=1` 的 server_default 兜底。
