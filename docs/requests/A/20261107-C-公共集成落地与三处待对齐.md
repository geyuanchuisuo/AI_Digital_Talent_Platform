## 待对齐三处（按影响排序）

### 1. `CTimestampMixin` 与公共 `UpdatedAtMixin` 行为不一致（建议收敛）

- 现状：C 域 21 表用 `app/modules/assessments/models.py` 的 `CTimestampMixin`，`updated_at` 由应用层维护，**无 `ON UPDATE CURRENT_TIMESTAMP`**；公共 13 表用 `app/models/base.py` 的 `UpdatedAtMixin`，由 MySQL 维护。
- 影响：同一仓库两类时间戳语义并存；C 表 UPDATE 后 `updated_at` 不自动刷新（若 C 应用层漏写就是静默数据陈旧）；`test_models_structure.py` 目前对两类表分别断言（差异已如实登记）。
- 你的公共集成请求验收里有「不重复定义公共 `UpdatedAtMixin`」——`CTimestampMixin` 目前事实上重复了该职责。
- **请求**：C 把 `CTimestampMixin` 收敛到公共 `UpdatedAtMixin`（或等价地给 updated_at 加 `server_default` 含 `ON UPDATE`），并随表结构变化提交 `C_*.py` 迁移（已有库的 C 表列默认值变更需迁移）。收敛后 A 会把结构测试的 C 域特例断言收紧回公共口径。
- 若 C 域确有「测试环境 SQLite 兼容」需求：公共 mixin 的 `server_default` 在 SQLite 下同样可建表（本项目结构测试即用 MySQL dialect 纯内存编译），请先验证再回复是否确有必要保留应用层维护。

### 2. `registry.py` 模型与路由捆绑导致加载环（A 侧已绕开，建议拆分）
