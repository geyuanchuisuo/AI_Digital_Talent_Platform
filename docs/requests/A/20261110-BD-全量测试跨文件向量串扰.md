- 关联：[A06-5 记录](../../updates/A/20261110-1430-A06-5跨模块行级判定迁移.md)

## 一、现象

后端全量（隔离库 `ai_talent_a_probe`）稳定出现 1 例失败：

```
FAILED tests/test_parse_integration_t13.py::test_full_pipeline_success
    assert len(fakes.store.upserts) == 1
    AssertionError: assert 2 == 1
    upserts = [(1001, 'a986cd4f...'), (<本次 profile id>, '49beb040...')]
```

`t13` 的 `fakes` 是 **function-scope**，每次新建 `FakeStore`，理论上不应有残留；
但 `1001` 那条固定 id / 固定 `text_hash` 会在**该用例执行期间**串进它的 FakeStore。

## 二、实证（全部真实退出码）

| 实验 | 命令 | 结果 |
|---|---|---|
| t13 单文件 | `pytest tests/test_parse_integration_t13.py` | **exit 0，13 passed** |
| 失败用例隔离单跑 | `pytest tests/test_parse_integration_t13.py::test_full_pipeline_success` | **exit 0，1 passed**（重复 2 次一致） |
| **两文件组合（零 A06 测试）** | `pytest tests/test_milvus_store_unit.py tests/test_parse_integration_t13.py` | **exit 1，同一断言失败**（`34 passed / 1 failed`） |
| 全量 | `pytest` | **exit 1**，827 passed / 8 skipped / 1 failed；A06-3 轮曾复跑 exit 0（间歇性） |

**结论**：该失败与 A06-5（以及任何 A 侧改动）**无因果关系**——仅跑两个非 A06 测试文件即可复现。
A 已排除另外两个假设：
1. 在 A 归属 `tests/conftest.py` 加用例边界 `milvus_store.reset_store()` 的 autouse 隔离 → **无效，已回滚**；
2. 清理隔离测试库遗留数据（236 `resume_pages` / 366 `parse_attempts` / 10 `parsed_resumes` / 10 `resume_files`）→ **无效**。

故判断为 `test_milvus_store_unit.py`（D）与 `test_parse_integration_t13.py`（B）之间对
`milvus_store` 模块级状态（单例 / 类方法 / 模块级缓存引用）的**跨文件串扰**。

## 三、影响

- 全量门禁无法稳定 `exit 0`，A 侧每台单元都要额外做「隔离单跑 + 串行复跑」定性，成本持续增加。
- **不影响生产代码**：`test_full_pipeline_success` 隔离单跑恒通过；失败只在特定文件组合/全量顺序下出现。
- 与本次 A06-5 的权限判定改动无关（A06-5 未触及 `parse_worker` / `milvus_store` / 向量链路）。

## 三之二、精确根因定位（A 实证，供 D 直接排查）

`tests/test_milvus_store_unit.py` 中 4 个 `sync_vector_by_text` 用例均传入固定
**`profile_id=1001`** 与固定文本 **`"画像文本"`**，并 `monkeypatch.setattr(ms, "get_store", lambda: store)`：

```
282: def test_sync_vector_by_text_success(monkeypatch):
285:     monkeypatch.setattr(ms, "get_store", lambda: store)
287:     result = ms.sync_vector_by_text(1001, "画像文本", persist_status=False)
294: def test_sync_vector_by_text_timeout_returns_failure_not_block(monkeypatch):
302:     monkeypatch.setattr(ms, "get_store", lambda: store)
305:     result = ms.sync_vector_by_text(1001, "画像文本", budget=0.05, persist_status=False)
...（313 / 328 / 335 处同样用 1001）
```

`t13.fakes` 则 `monkeypatch.setattr(milvus_store, "_default_store", store)`。
失败时串入的 `(1001, 'a986cd4f...')` 中，`1001` 与 `a986cd4f...`（`"画像文本"` 的
`text_hash`）与上述用例**完全对应**。结合用例名 `timeout_returns_failure_not_block` 与
`budget=0.05`，判断为 **超时路径返回后仍有后台/延迟写入未完成**，在后续 t13 用例的
`fakes` 生效窗口内落到当时的默认 store 上。这解释了：

- `1001` / hash 固定不变，而本次 parse 的 profile id 每次变化（860/920/954/768…）；
- 两条 upsert 的**先后顺序不稳定**（全量日志中 `1001` 有时在前、有时在后）→ 异步写入；
- 间歇性（A06-3 轮全量复跑曾 exit 0）；
- 为何 `reset_store()` 用例边界隔离无效（不是单例残留，而是延迟写入到「当前」store）；
- 为何清理隔离库脏数据无效（与 DB 数据无关）。

> 建议 D 重点检查 `milvus_store.sync_vector_by_text` 的 `budget` 超时实现：
> 超时返回后必须取消/等待后台任务，且写入应绑定到调用开始时的 store 引用，
> 不要在超时后再读取全局默认 store。

## 四、建议修复方向（由 B/D 决定，A 不代改）

1. 定位 `1001` / `a986cd4f...` 的来源：疑似 `test_milvus_store_unit.py` 中 `store.upsert(1001, ...)`
   相关用例或 `sync` 路径用例持有模块级引用，写入了后续用例注入的 `FakeStore`。
2. 让 `test_milvus_store_unit.py` 的用例在 teardown 显式还原所有 monkeypatch 的模块级引用
   （含 `get_store` / `_default_store` / 类方法），或用 fixture 把状态隔离到单文件内。
3. 或让 `test_parse_integration_t13.py` 的 `fakes` 在 setup 时清空并重新绑定所有向量入口，
   使其不依赖前一个文件的全局状态。
4. **不建议**放宽 `len(upserts) == 1` 断言（那是有效断言，不应删弱）。
