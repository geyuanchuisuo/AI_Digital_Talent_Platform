## 根因分析（建议 A 复核）

1. `backend/tests/conftest.py` 的 `_isolate_task_runner` 是**函数级 autouse**，通过 monkeypatch
   把 `app.tasks.runner.runner.start/stop` 打成空操作；但 `test_match_batch_t25.py` 的 `client`
   是**模块级** fixture。pytest 先实例化高 scope fixture，因此模块首个用例进入 `TestClient(app)`
   的 lifespan 时 patch 尚未生效，真实 `TaskRunner` 会启动并在整个模块内每 2 秒扫描。
2. 测试随后直接调用 `handle_match_batch(batch_id)`，而
   `backend/app/tasks/match_worker.py` 只拒绝非 `running/pending` 状态；后台 runner 抢先认领
   同一批次后，直接调用仍会执行，两个执行体都通过各自的 `written` 检查，导致同一
   `(batch_id, talent_id)` 重复插入；LLM 调用数也因此多 1。
3. 复现窗口小，是否命中取决于 runner 扫描时机与机器负载；本次全量运行恰逢并发负载，概率上升。

## 建议修复方向

- 测试隔离：把 `client` 改为函数级，或在模块级 fixture 创建 `TestClient` 前先完成 runner patch；
  确保非 `real_runner` 用例不会启动真实扫描线程。
- 如希望防御直接调用与后台 runner 的双执行，可将 `handle_match_batch` 的入口状态收窄为
  `pending` 并通过条件更新原子认领；`running` 批次只允许 heartbeat/恢复逻辑处理，而非再次执行。
- 补一条回归：在真实 runner 已启动的情况下调用 handler，断言只产生一份结果。
