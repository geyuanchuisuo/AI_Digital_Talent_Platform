# 请求：OCR 与 PDF 页渲染能力接入

- 请求 ID：REQ-B-20261106-01
- 请求方：B（文件/OCR）
- 目标维护人：A（公共依赖、配置、启动集成）
- 对应需求：F02 图片/扫描件解析
- 状态：待处理；未安装、未验证

## 目标

让 B 能在现有解析流水线中处理 JPG/PNG 图片、扫描版 PDF 和混合 PDF，并保留逐页文本与页码证据。

## 现状

- `backend/app/service/extract_service.py` 只做 pypdf 文本提取与 python-docx 解析，明确不处理扫描件。
- `backend/app/config.py` 扩展名白名单只有 pdf/docx。
- 后端没有任何 OCR/PDF 渲染依赖（已检索，无 paddle/tesseract/rapidocr/pymupdf 等）。

## 请求 A 提供

1. 批准并安装以下候选依赖到后端公共依赖清单与锁文件：
   - `rapidocr-onnxruntime`（本地 ONNX OCR，Windows 离线可用，无需系统级二进制）
   - `pymupdf`（PDF 页渲染）
   - `pillow`（图片解码）
2. 将 OCR 模型文件放到仓库约定目录（建议 `backend/models/ocr/` 或部署目录），并在启动/健康检查中校验缺失时明确报错。
3. 增加配置项：OCR 开关、模型目录、单页像素上限、最大页数、OCR 超时；默认值由 A 与 B 共同确认。
4. 提供安装说明与离线部署说明，不要求运行时联网。

如 A 已有其他 OCR 方案或镜像限制，请给出替代包与版本，B 按同一适配层接入。

## B 承诺的实现

- 在 `extract_service.py` 增加 OCR 适配层，图片与扫描页走 OCR，文本层优先，混合 PDF 逐页判断。
- 逐页返回：页码、文本、是否 OCR、页质量标记、失败原因。
- OCR 依赖缺失或模型缺失时，任务明确失败并给出可理解提示，不返回虚构档案。
- 用虚构样例验证 JPG/PNG/扫描 PDF/混合 PDF，记录真实结果。
- 不修改 `requirements.txt`、锁文件、公共配置和启动脚本，这些由 A 完成。

## 兼容与影响

- 新增依赖会增加安装体积与首次加载时间；需在部署说明中写明。
- 不影响已有 PDF/DOCX 路径；OCR 失败不回滚整批。
- 无数据库结构变化。

## 验收

- 一张 JPG、一张 PNG、一份扫描 PDF、一份混合 PDF 均能提取文本并进入解析。
- 模型/依赖缺失时任务失败原因明确且可重试。
- 单页超像素/超页数限制生效，逐文件返回原因。
- 运行时无外网依赖。
