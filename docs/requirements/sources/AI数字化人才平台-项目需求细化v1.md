## 0. 阅读说明与确认规则

### 0.1 目标

将现有 PRD、原型、概要/详细/接口/数据库设计和测试材料整理为可追踪、可讨论、可验收的单一需求基线，明确业务范围、角色权限、AI 质量、安全、交付边界和未决选择。

### 0.2 状态标记

- **建议**：为便于讨论提出的默认方向，未经用户确认不得自动升级为承诺。
- **待确认**：需要产品/业务/技术负责人回答的问题。
- **目标值（待确认）**：源材料出现的指标，尚未完成可测性、成本与可达性论证。
- **示意**：原型中的虚构/样例数据或交互，不构成正式需求或现状证明。

### 0.3 需求变更与实施门槛

1. 先确认本文件中的范围、优先级、角色权限、指标及技术约束。
2. 需求确认后，再形成独立开发计划与待办清单，交用户审核批准。
3. 用户明确说“开始”之前，不编写或修改业务代码；需求文档、原型讨论和分析不视为开始开发。
4. 需求冻结后，每项变更须记录原因、影响模块、验收口径、数据/安全影响及批准人；同步更新需求追溯关系。

## 2. 项目定位与目标

### 2.1 暂定定位

面向企业人才招聘与人才发展场景的 AI 辅助平台。通过结构化人才数据、岗位/项目需求、测评培训、知识检索和可控 AI 工作流提升人才信息处理与决策效率。AI 输出用于辅助，不自动替代招聘、晋升、薪酬等需要人工负责的决定。

> “企业级、AI 原生、全流程智能化”来自既有材料；具体面向外部招聘还是内部人才发展、哪些流程纳入首版，待 D-02/D-03 确认。

### 2.2 暂定业务目标

1. 建立统一的人才档案与来源可追踪的数据基础。
2. 减少简历录入、筛选、岗位匹配等重复操作，并支持人工复核。
3. 将岗位要求、匹配依据及候选人评估过程结构化留存。
4. 为已批准的知识内容提供有权限、可溯源的问答。
5. 在权限、审计和评测机制到位后，逐步扩展人才发展和数据决策能力。

### 2.3 七问（需求基线）

| 问题 | 当前理解 | 待确认 |
|---|---|---|
| 为谁解决 | HR/招聘、业务负责人、员工、管理层、平台管理员 | D-03、D-09 |
| 解决什么 | 人才数据分散、筛选匹配效率低、评估与培养信息不连贯 | 业务方是否认同、优先痛点 |
| 核心价值 | 减少人工重复处理，提升人才信息可用性与可解释性 | 量化基线/目标 |
| 关键流程 | 人才入库、岗位需求、匹配评估；其他流程待选 | D-02、D-08 |
| 数据来源 | 简历、组织/岗位、测评、课程、知识文档、外部系统 | 系统清单、授权、数据负责人 |
| 成功标准 | 功能闭环、权限正确、AI 指标经标注集验证、交付可部署 | D-15、D-16、D-20 |
| 明确不做 | 未获批准的自动录用/淘汰决定；未批准的数据外发；未确认范围的模块 | 还需补充排除项 |

- **P3**：体验优化、低频场景或特定环境适配。

暂不为模块强行分配 P0/P1，待 D-02 确认后建立首版范围矩阵。不得把原 PRD 的覆盖面直接视为首版承诺。

## 4. 术语与业务规则

| 术语 | 定义/待确认点 |
|---|---|
| 人才档案 | 统一人才实体；须区分内部员工与外部候选人，避免同一身份重复建档。 |
| 候选人 | 参与某招聘流程的外部人才记录；与人才档案关系及生命周期待定。 |
| 岗位 | 企业岗位或招聘职位；岗位编制、职位发布、JD 的关系须在领域模型中明确。 |
| 项目人才需求 | 项目/业务负责人提出的人员需求，含技能、人数、期限、组织归属及审批状态。 |
| 匹配分 | AI/规则给出的辅助排序结果，必须显示依据、缺失数据与不确定性；不直接作为淘汰决定。 |
| AI 生成内容 | 简历字段、标签、匹配解释、问答/报告等模型产出；应保留生成来源、模型版本、时间及必要的人工修订记录。 |
| 知识来源 | 作为回答依据的文档、版本、章节/页码/片段；展示前须确认当前用户有权访问。 |
| 幂等请求 | 重复提交同一业务操作不会重复创建副作用；作用范围和幂等键策略需在接口契约中定义。 |
| 待确认状态枚举 | 简历解析、候选人阶段、岗位需求、面试、测评、培训、Agent 运行状态须各有单一事实源；需在接口/领域设计冻结前集中确认，禁止前后端自造字符串。 |

### 4.1 通用状态机要求

每个可重试的异步任务至少定义：初始/排队、执行中、成功、失败、取消（如适用）状态；明确合法迁移、重试策略与上限、最终失败呈现、人工重跑规则、重复提交行为和审计信息。业务审批状态不得与技术任务状态混用。具体枚举表作为需求确认后的设计产物。

## 5. 角色与权限（候选模型）

以下为最小候选角色，不代表最终授权。权限以用户身份、组织归属、业务关系、角色与显式授权组合判定；“管理员”不能默认绕过所有数据访问审计。

| 候选角色 | 可能业务职责 | 默认数据范围建议（待确认） |
|---|---|---|
| 普通员工 | 个人档案、测评、学习、员工可见知识问答 | 仅本人及明确授权数据 |
| HR/招聘 | 候选人、岗位、招聘流程与邀约 | 授权组织/招聘项目；敏感字段按权限最小化 |
| 业务负责人 | 项目需求、岗位匹配与面试反馈 | 所属组织/项目及被授权人才 |
| 面试官/评估人 | 受邀面试、提交评估 | 仅被分配的招聘/面试对象 |
| 管理层 | 汇总指标与授权决策信息 | 授权组织汇总；避免默认暴露个人敏感信息 |
| 组织管理员 | 用户、组织与部门配置 | 管理授权范围内的组织数据 |
| 系统管理员 | 系统配置、运行维护 | 配置管理与必要的受控运维访问；访问业务敏感数据需单独授权/留痕 |

### 5.1 权限验收要求

1. 未登录或凭证失效访问受保护资源时拒绝访问；拒绝响应不泄露资源是否存在等不必要信息。
2. 每个读写/导出/搜索/问答/报表/后台任务入口都须进行服务端授权；前端隐藏菜单不算权限控制。
3. 行级范围在查询执行前生效；字段级规则同时作用于详情、列表、搜索、导出、日志和 AI 上下文，避免侧信道泄漏。
4. AI/RAG/问数的检索候选集须先按调用用户权限过滤；不得仅在生成后过滤答案。
5. 角色变更、撤权、停用后，后续请求按新权限生效；缓存/会话失效时限由 D-10 决定。
6. 越权行为应拒绝并按安全策略记录审计事件；日志避免记录不必要的简历正文、凭证或敏感提示词。
7. 导出、批量下载、敏感字段查看及管理员授权变更须明确授权、审计、限额/审批策略。

> 行级/字段级权限矩阵需根据 D-09 的最终角色逐资源逐字段补齐，当前不可将源测试文档中的示例矩阵当作已批准策略。

## 6. 功能需求（草案）

所有条目状态均为**待范围确认**。下列验收标准描述需求应达到的可观察行为；未确认的数据源、指标、角色、页面和目标值均以待确认处理。

### 6.1 身份、组织与权限（IAM）

#### REQ-IAM-001 身份认证与会话

系统应支持经批准的身份认证方式，提供登录、退出、会话失效处理及受保护资源访问控制。

- AC-1：有效身份按所选认证方案登录成功；无效/过期凭证不能访问受保护接口。
- AC-2：退出或管理员停用/撤销身份后，旧会话在确认的失效窗口内不可继续访问。
- AC-3：认证失败提示不泄露账号是否存在或敏感认证细节。
- 来源：PRD 的登录/令牌测试要求；认证供应商与流程待 D-10。

#### REQ-IAM-002 用户、组织、角色与授权

授权管理员按权限维护用户状态、组织关系、角色及数据范围，并能查询授权变更记录。

- AC-1：未授权用户无法创建/变更角色、组织或授权。
- AC-2：用户停用、离职或组织变化后，已定义的访问与任务处置规则生效。
- AC-3：授权变更记录操作者、时间、对象、变更前后值及结果，敏感值按策略脱敏。
- 来源：PRD 系统管理；现有角色与组织归属待 D-09。

#### REQ-IAM-003 权限贯穿与审计

所有业务查询、写入、批量操作、导出和 AI 调用均执行统一权限策略并产生必要的审计记录。

- AC-1：跨组织/跨候选人未授权访问在服务端被拒绝，列表、详情、搜索和导出结果一致受限。
- AC-2：审计可按用户、时间、对象、操作、结果查询；不得将秘密或不必要的个人数据写入日志。
- AC-3：高风险权限变更、数据导出与敏感信息访问产生可追溯事件。
- 来源：PRD 2.8、测试用例权限/审计章节；字段清单待确认。

### 6.2 人才档案与简历（TAL）

#### REQ-TAL-001 简历导入与来源登记

授权人员可导入单份或批量简历；系统保存来源、上传人、上传时间、文件标识、处理状态及必要的授权/告知信息。

- AC-1：支持格式、大小、数量及恶意/损坏文件处理规则明确后，合法文件可提交并返回逐文件受理结果。
- AC-2：不支持或无法读取的文件明确失败原因，不伪报成功；不会生成不完整的“成功”档案。
- AC-3：重复请求不会重复创建文件/解析任务；批次部分失败时可区分成功与失败项。
- AC-4：原始文件访问受权限控制，存储与保留期限遵从确认的合规策略。
- 来源：PRD 2.1、TC-RES-01；格式与限制待确认。

#### REQ-TAL-002 简历解析与人工校正

系统按已确认的字段字典从简历提取结构化信息，显示字段来源/置信度或待复核提示，并允许有权人员校正。

- AC-1：解析结果与原文件及解析版本关联；字段包括经确认的姓名/联系方式/教育/经历/技能等。
- AC-2：低置信度、缺失或冲突字段可被识别并进入人工复核，不擅自补造事实。
- AC-3：失败任务说明可理解的原因，并按策略安全重试；同一任务重复执行不会重复创建人才实体。
- AC-4：人工修订记录操作者、时间及字段变更；可区分原始抽取值与确认值。
- AC-5：解析准确率目标及统计方式依据 D-15 确认后验收；不得用少量示例样本宣称达标。
- 来源：PRD 2.1、TC-RES-02/03、评测集 `docs/test/data/resume_parse_eval.json`（当前示例规模不足）。

#### REQ-TAL-003 人才档案、标签与查重

授权人员可查看/维护人才档案，生成或维护标签及档案完整度；系统提示潜在重复记录，合并由有权人员确认。

- AC-1：档案字段、标签分类/词典、来源及更新时间可追溯。
- AC-2：疑似重复项提供可比较依据；未经确认不得不可逆地自动合并。
- AC-3：合并保留来源记录和可审计的关联/撤销方案，不丢失原始文件和关键历史。
- AC-4：个人敏感字段按权限掩码显示，导出同样受限。
- 来源：PRD 2.1、原型人才画像/查重区域；“百级标签”及自动合并阈值待确认。

#### REQ-TAL-004 人才检索与档案问答

授权人员可用结构化条件及自然语言检索授权范围内人才；档案问答仅依据有权访问的档案内容，并展示依据。

- AC-1：组合筛选、分页/排序及空结果状态符合接口契约。
- AC-2：搜索结果不能包含调用者无权访问的个人或字段信息。
- AC-3：AI 回答区分事实、推断与无依据内容；引用可定位到档案字段/来源材料。
- AC-4：无足够依据时明确说明无法判断；问答输入、输出和引用遵循审计/保留策略。
- 来源：PRD 2.1、原型人才画像页；检索范围与模型待确认。

### 6.3 岗位、需求与招聘（JOB）

#### REQ-JOB-001 岗位/JD 与项目人才需求

授权业务人员可维护岗位要求及项目人才需求；需求包含数量、职责/技能、组织、优先级、时间范围和审批信息等经确认字段。

- AC-1：必填字段、合法状态流转、组织/项目授权规则有统一定义。
- AC-2：变更保留历史版本；匹配任务可追溯到使用的岗位/JD 版本。
- AC-3：项目需求未经授权不可见/修改；重复提交同一创建请求不产生重复需求。
- 来源：概要设计项目需求/岗位域、PRD 2.3；字段和审批规则待确认。

#### REQ-JOB-002 人才—岗位匹配

系统根据经批准的岗位条件和可访问人才数据计算候选匹配结果，提供排序、分项依据、缺失数据及人工复核入口。

- AC-1：匹配结果关联岗位版本、人才档案版本、规则/模型版本及计算时间。
- AC-2：评分范围、维度权重与阈值可解释；不得将模型分数描述为客观录用结论。
- AC-3：无关/缺失资料不被默认为满足条件；结果展示不确定性和需要人工核验项。
- AC-4：候选集合严格受调用者权限约束；重复触发具备去重/幂等或明确任务语义。
- AC-5：匹配质量指标按 D-15 定义的标注集和判定方法评估。
- 来源：PRD 2.3、TC-MAT-01~04、`match_eval.json`（现有样例规模不足）。

#### REQ-JOB-003 候选人流程与人工决策

授权招聘人员可管理候选人阶段、负责人、面试/评估记录及决策结果；状态变更须合法且可追踪。

- AC-1：阶段、可执行动作、必填条件及驳回/撤回规则定义为单一状态机。
- AC-2：每次状态变更记录操作者、时间、原因及关联招聘需求。
- AC-3：AI 建议不能自动淘汰、录用或改变候选人阶段，除非另有经批准且合规的明确流程。
- AC-4：被授权面试官只可访问分派范围内信息；评估记录访问/修改留痕。
- 来源：PRD 中候选人管理、概要设计招聘流程；具体阶段及人工决策责任待确认。

#### REQ-JOB-004 邀约、面试与通知

按批准范围创建邀约、安排面试时间/参与者、发送通知并记录反馈与后续状态。

- AC-1：日历冲突、取消/改期、通知失败、候选人拒绝等路径有明确状态和用户提示。
- AC-2：外部消息只发往已确认的渠道/接收方；重试不重复发送造成重复邀约。
- AC-3：面试记录及附件仅向授权人员开放；保存期限待确认。
- 来源：概要设计 `jd_publications`、`interview_invites`、`multi_round_interviews`；渠道与模态待 D-08/D-14/D-19。

### 6.4 测评与面试评估（ASM）

#### REQ-ASM-001 题库、测评配置与作答

授权人员维护题目及测评配置；参与者仅能访问分配给自己的有效测评并提交作答。

- AC-1：题目、选项/标准答案、评分规则、版本和可见范围明确；题库变更不追溯篡改已开始的测评。
- AC-2：重复提交、超时、断线恢复、已提交再次提交均有明确且一致的处理。
- AC-3：评分结果可追溯到测评配置/试卷版本；人工评分可记录评分人和理由。
- 来源：PRD 2.2、测试用例 TC-EXM-01/03；考试模式和规则待确认。

#### REQ-ASM-002 能力分析与面试辅助

系统可根据测评及经授权的面试反馈形成辅助分析，标明数据来源与评估局限。

- AC-1：能力维度、评级规则及雷达图指标定义明确，不以无数据的静态示意数值冒充结果。
- AC-2：AI 面试若纳入，模态、告知/同意、录制、转写、保留和删除机制先获批准。
- AC-3：输出为辅助评估，可被人工复核、更正并记录；不自动作出雇佣决定。
- 来源：PRD 2.2、原型智能测评、TC-EXM-04/06；D-14。

#### REQ-ASM-003 错题复盘与复习计划

在范围内时，系统依据已提交测评生成错题清单和可调整的复习计划。

- AC-1：错题与原题/答案/测评版本关联，权限仅限本人及被授权管理者。
- AC-2：计划可查看、调整、完成或取消；建议来源可追溯，不声称未验证的能力提升。
- 来源：PRD 2.2、TC-EXM-05；首版范围待确认。

### 6.5 培训与成长（TRN）

#### REQ-TRN-001 培训方案与课程

在范围内时，授权人员维护课程/计划；员工查看分配内容、进度与完成记录，AI 推荐须提供推荐依据。

- AC-1：课程内容版本、目标人群、学时与完成条件有明确口径。
- AC-2：报名/分配、开始、进度、完成、取消的状态和记录一致可追溯。
- AC-3：AI 推荐不会自动改变员工考核或人事状态；无可靠数据时说明限制。
- 来源：PRD 2.4、概要设计培训域；首版范围待确认。

#### REQ-TRN-002 学习有效性与隐私

学习时长统计应采用已批准的低侵入策略；任何人脸/生物识别处理必须先过隐私与法律评估。

- AC-1：有效学时口径、心跳/活动判定、断线恢复、重复播放等规则公开且可复现。
- AC-2：不采集未批准的摄像头/生物特征数据；如经批准，提供告知、授权、访问/留存/删除和非生物识别替代路径。
- AC-3：异常判定允许人工复核与申诉，不能仅凭自动检测直接惩罚员工。
- 来源：PRD 2.4、原型“人脸抽检”内容；D-12。

#### REQ-TRN-003 成长轨迹

在范围内时，按权限展示人才的测评、学习和能力变化，并区分事实记录与推断。

- AC-1：每个时间点可追溯到实际测评/学习事件；无数据时显示空态而非虚构曲线。
- AC-2：本人可见范围、管理者访问范围和敏感评价字段按权限策略执行。
- 来源：PRD 2.4、原型培训页；指标模型待确认。

### 6.6 知识库与 RAG（KNO）

#### REQ-KNO-001 知识内容管理与索引

授权人员导入、更新、停用知识内容；系统记录文档版本、来源、权限标签、处理状态和索引版本。

- AC-1：重复导入、失败重试、更新及删除/停用的索引一致性有明确规则。
- AC-2：处理失败可定位阶段与原因；重试不会产生重复有效内容。
- AC-3：文档原件、切片和向量访问均执行权限策略；删除/撤权在确认的时限内影响检索。
- 来源：PRD 2.6、TC-RAG-01、知识库设计；支持格式/切片策略待确认。

#### REQ-KNO-002 有权限、可溯源的问答

系统仅用调用者有权访问的知识检索并回答；回答展示可验证的来源引用，对证据不足的问题拒答或说明不确定性。

- AC-1：引用可定位文档及经确认的章节/页码/片段，引用内容确实支持回答。
- AC-2：越权知识不进入模型上下文，答案/引用/摘要均不得泄漏。
- AC-3：无依据问题不编造政策条款；拒答原因对用户清晰。
- AC-4：评测集规模、样本分层、答案正确及引用正确的判定方法按 D-15 批准后验收。
- AC-5：记录必要的模型/索引/提示版本、耗时和结果状态；日志最小化保存个人信息。
- 来源：PRD 2.6、TC-RAG-02~04、`rag_eval.json`（当前示例规模不足）。

### 6.7 Agent 与工作流（AGT）

#### REQ-AGT-001 Agent 配置、版本与运行记录

授权管理员可查看/维护经批准的 Agent 配置及版本；运行任务可追踪输入引用、状态、结果与失败原因。

- AC-1：草稿、测试、发布、停用/回滚等生命周期明确；发布有权限检查与版本记录。
- AC-2：运行日志不暴露凭证或不必要的个人数据；敏感输入按策略脱敏/限制访问。
- AC-3：模型/外部工具调用有超时、失败处理、人工重试或取消机制。
- 来源：PRD 2.7、测试用例 TC-AGT-01；D-05。

#### REQ-AGT-002 工作流编排与人工确认

在批准的编排能力范围内，用户可创建/运行有界工作流；涉及外发、数据变更或影响候选人状态的操作须经过明确授权及必要的人工确认。

- AC-1：每个节点定义输入/输出契约、错误路径、超时与重试上限；流程版本不可静默改变正在执行的实例。
- AC-2：外部副作用具备幂等保护；失败实例可追踪并按权限重试/取消。
- AC-3：Agent 不直接绕过业务服务/权限层修改数据库；所有写入经受控业务接口及审计。
- AC-4：可视化画布、分支和拖拽能力仅在明确纳入 D-05/D-08 后验收。
- 来源：概要/详细设计工作流、PRD 2.7；D-05。

#### REQ-AGT-003 定时任务与数字员工

定时任务/数字员工仅在已确认的具体场景、授权和责任人下执行；每次运行可暂停、取消或转人工处理。

- AC-1：调度时区、错过执行、重叠执行、失败重试、最大重试与告警策略明确。
- AC-2：外发消息、资料变更和候选人阶段变更须限制权限并按需人工批准。
- AC-3：能够查看任务责任人、执行记录、错误与人工接管情况。
- 来源：PRD 2.7、概要设计 `task_scheduling`/`digital_bot`；D-18。

### 6.8 数据决策（DEC）

#### REQ-DEC-001 受控指标查询

若纳入范围，用户可查询经批准的数据指标；查询数据集、指标定义和组织范围由服务端授权并限制。

- AC-1：查询只能访问白名单数据集/指标；禁止任意写操作、DDL、越权表/字段访问。
- AC-2：自然语言请求无法安全映射时，系统拒答或请求澄清，不执行猜测查询。
- AC-3：结果携带查询范围、数据更新时间、指标定义及必要的来源信息。
- AC-4：生成图表/报告不扩大原查询数据权限；导出另行校验授权并审计。
- AC-5：NL2SQL 引擎选型及 SQL 生成/执行模式按 D-06 确认；建议先提供有限指标语义层，而非任意 SQL。
- 来源：PRD 2.5、TC-DEC-01~03；D-06、D-09。

#### REQ-DEC-002 决策建议与审计

AI 建议须区分事实与建议，显示数据依据与限制；不得将相关性描述为因果性，或自动执行人事决策。

- AC-1：建议关联查询结果、时间范围、生成版本和用户权限范围。
- AC-2：无足够或过期数据时显式提示；用户可反馈/标记不准确。
- AC-3：问数审计记录操作者、查询意图、数据范围、执行状态和耗时；按数据最小化原则处理具体 SQL/提示词。
- 来源：PRD 2.5；准确性与审计口径待确认。

### 6.9 通知与运营（OPS）

#### REQ-OPS-001 通知与任务状态

对经确认的重要事件提供可见状态/通知，区分待办、成功、失败和需要人工处理的事件。

- AC-1：通知渠道、订阅规则、频率、模板和保存期经 D-19 批准。
- AC-2：通知失败可查看并按策略重试；幂等防止重复通知。
- AC-3：站内通知权限与源业务对象权限保持一致。
- 来源：原型/概要设计工作流输出通知；D-19。

#### REQ-OPS-002 运营指标与健康状态

系统按权限展示可验证的业务/运行指标，明确数据窗口和更新时间；示意数据不可作为真实运行数据。

- AC-1：每个指标有定义、计算口径、数据来源和更新时间。
- AC-2：无数据或采集失败时显示不可用/空态，不以常量填充。
- AC-3：敏感业务数据的汇总结果也执行权限与最小群体披露策略（如适用）。
- 来源：原型智能工作台/技术差距页、PRD 非功能要求；页面是否对用户开放待 D-08。

## 7. 数据、接口与状态要求

1. **接口契约先行**：写接口前确认请求/响应、错误码、分页/排序、过滤、权限、幂等键、版本与兼容策略；OpenAPI 与需求保持一致。
2. **边界统一**：外部输入在接口层校验；服务端执行权限与业务规则，数据访问经统一的数据访问层；AI 工具不得绕过业务服务直写数据库。
3. **失败可见**：网络/模型/文件解析/存储/索引/消息失败须可识别、可重试或明确终止；不向用户谎报成功，不泄露内部密钥和堆栈。
4. **幂等与并发**：导入、创建、提交、任务触发、消息发送等可能重复的操作定义幂等范围、并发冲突处理及唯一约束策略。
5. **审计**：授权变更、敏感信息访问、导出、人工校正、AI 决策辅助及高风险任务须按策略记录谁、何时、对什么对象、做了什么、结果如何。
6. **枚举单一来源**：所有状态、角色、权限、错误码和任务类型由契约/领域定义生成或共享，禁止前后端各自维护不一致的字符串。
7. **迁移与数据质量**：每次 schema 变更需有可审查迁移、回滚/恢复策略（适用时）、数据校验及升级顺序；迁移操作可审计。
8. **种子数据**：仅用于开发/测试，不得混入生产；数据字典、SQL 与测试说明需保持一致，不使用真实个人简历或未经授权个人信息。
9. **历史材料差异**：`docs/test/seed_data.sql` 的表数量与 `测试数据.md` 所称核心表数量不一致；`knowledge_chunks.milvus_id` 的 NULL 占位说明与 SQL 示例值不一致。需在技术设计冻结前统一，不据此推断生产 schema。
10. **未定义表/模块**：历史材料提及 `workflow_run` 等对象但没有完整表定义；须先明确是否纳入需求，再更新数据模型。

## 8. 非功能、安全与 AI 质量要求

### 8.1 性能与容量（均待 D-16 确认）

现有材料提出：在线并发≥2000、页面渲染≤1s、普通接口≤1s、报表≤3–5s、向量检索≤500ms、全年可用率≥99.9%、AI 服务≥99.5%、缓存命中率≥98%。这些数字尚缺负载模型、统计分位数、部署规格和测量环境，当前仅作待确认目标。

验收前至少定义：并发用户与请求混合、数据规模、冷/热缓存、外部模型响应是否计入、P95/P99、错误率、采样窗口、压测工具/环境和报告格式。不得把原型静态指标当成实测。

### 8.2 安全与隐私

- 个人信息处理遵循目的明确、最小必要、权限最小化、保留期限和删除机制；具体合规义务须由项目法务/安全负责人确认。
- 简历、联系方式、评估、面试录音录像、学习监控、人脸/生物识别属于需重点评估的数据；默认不扩展采集用途。
- 传输、存储加密与密钥管理方案待安全设计；密钥不得进入源码、日志或错误响应。
- 文件上传实施类型/大小校验、恶意内容检测与安全存储；文件下载防止未授权访问与路径越权。
- 防止提示注入、越权 RAG、模型输出注入、敏感信息泄露；模型输出作为不可信数据处理，不直接执行命令/SQL或外部副作用。
- 保留审计、备份、恢复、删除和事件响应策略；备份也须执行访问控制和保留策略。
- 国产化、私有化目标按 D-17 明确供应商、版本和验证标准。

### 8.3 AI 评测与人工监督

| 能力 | 历史材料目标 | 评测要求草案 | 现状/风险 |
|---|---:|---|---|
| 简历解析 | ≥99% | 明确字段级/样本级口径、精确率/召回率/F1、字段权重、文档类型分层与人工抽查 | 现有 `resume_parse_eval.json` 仅示例规模；不足以验收 |
| RAG | ≥95% | 分别衡量检索命中、答案正确、引用正确、拒答；纳入越权与无依据问题 | `rag_eval.json` 仅示例规模；定义混合“准确率”会误导 |
| 岗位匹配 | ≥90% | 定义正例/负例、排序指标或阈值一致率、岗位分层及人工标注一致性 | `match_eval.json` 仅示例规模；偏差/公平性规则未定 |

- 数据集至少覆盖目标场景、困难样本、不同输入质量和越权/拒答边界；样本数应通过统计与业务风险评估确定，而不是仅达到固定数量。
- 评测集需版本化、去重、标注双人复核/仲裁，记录数据授权和敏感信息处理；生产数据用于评测须经批准。
- 模型、Prompt、检索配置或规则变更需回归评测；上线阈值、回滚条件和人工复核抽样率待确认。
- AI 输出需能追溯模型/配置版本和必要输入来源；不承诺“零幻觉”。
- 人才筛选/评估须有人类监督、纠错和申诉路径；不得把未经验证的分数当作唯一决策依据。

### 8.4 可用性与可维护性

系统需为无数据、加载中、部分失败、无权限、服务不可用、模型超时、提交重复和任务失败提供一致可理解的反馈；运维侧可定位请求/任务并关联日志指标。具体可用率、恢复时间目标、恢复点目标、告警渠道与值班责任待 D-16/D-20 确认。

### 8.5 多端与无障碍

需确认 D-11 后定义支持的浏览器/视口、响应式断点、键盘操作、表单错误提示和图表替代文本。现有原型主要为桌面静态线框，不能视为移动端验收依据；原型亦未完整覆盖登录、空态、错误态。

## 10. 测试与验收策略

### 10.1 需求追溯

每条批准需求须关联至少一个验收场景；P0 需求关联端到端测试、权限测试和失败路径测试。接口、原型、测试用例与用户手册的名称/状态枚举须基于同一契约。

### 10.2 测试层次

- 单元/组件：业务规则、状态流转、评分/权限决策。
- 集成：真实测试数据库/对象存储/向量检索/模型替身边界；对外部供应商可用受控契约测试，但不能以 mock 代替关键数据安全与持久化验收。
- 端到端：经批准主流程，使用可复现测试数据并验证失败/重试/重复提交。
- 安全：角色、行级、字段级、导出、RAG、问数及管理操作越权测试。
- AI 评测：固定版本标注集、基线对比、模型/配置回归和人工抽检。
- 性能/恢复：按确认的容量方案压测，验证任务积压、外部模型超时与恢复行为。

### 10.3 交付验收门槛（草案，待批准）

1. 所有批准的 P0 需求通过率 100%，阻断级安全问题为零；P1 门槛由项目方确认。
2. P0 端到端流程以真实后端持久化数据通过，包含失败、重复请求、权限与审计断言。
3. AI 指标只在 D-15 批准的评测集/公式上验收，并提交数据集版本、评测报告和误差分析。
4. 性能、安全、隐私、兼容性达到经批准的目标，并提供可复核报告。
5. 数据迁移/备份恢复/部署文档、运维手册、已知限制、交付清单和验收记录齐备。
6. 所有示意数据与演示账户清楚标识，不将原型静态内容作为验收通过证据。

## 12. 工程与协作纪律（项目执行约束）

1. 先确认需求，再制订开发计划/todolist；用户明确说“开始”前不写代码。
2. 接口契约优先于前后端实现；错误码、字段、状态枚举保持单一事实源。
3. 保持分层边界；Agent/LLM 不得直接操作数据库或绕过鉴权执行业务副作用。
4. 设计失败路径、幂等、重试上限和审计，不以无限重试掩盖错误。
5. schema 变化配迁移与数据验证；测试环境与交付环境差异须显式记录。
6. 禁止以 mock/固定常量冒充生产数据或最终验收；mock 仅用于适当的隔离测试并明确边界。
7. UI 修改须在可运行环境验证主路径与边界状态；无法运行验证时须如实说明。
8. 报告工作状态必须区分已完成、已验证、推断与待确认，不把历史 PRD 的“已落地”作为当前代码事实。
