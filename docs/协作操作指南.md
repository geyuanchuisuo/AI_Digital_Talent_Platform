# Git 与 Agent 协作操作指南

日期：2026-11-06。先读根 [AGENTS.md](../AGENTS.md)、[更新记录](../更新记录.md)、[模块归属](模块归属.md)。本指南只说明如何启用协作规则，不代表业务已开发或远端保护已设置。

## 1. 一次性准备（由小组维护人处理）

需求与协作基线已于 2026-11-06 发布到 `origin/master`（`5c3df08`）。后续规则、工具和业务改动均先在开发分支完成，再经用户明确授权集成发布；任何成员或 Agent 都不得在 `master` 开发、修改文件或创建开发提交。

每个人在自己的个人分支开发，开始修改前先检查分支；若在 `master`，先切回本人的开发分支。`master_YB` 仅是本次用户的个人分支，当前 Agent 为该用户工作时使用它；其他成员继续使用各自分支，不要求改名或切到 `master_YB`。不要根据分支名推断成员角色。精确暂存本人文件，不使用 `git add .` 混入其他内容。

这是启用检查前的一次建制提交：目录规则分布于四个工作包，不能套用某一个业务角色独立变更规则去验收该建制提交。基线合入后再启用正常角色检查，不设置永久 bypass 或让 A 获得任意业务写权限。

`.githooks/pre-commit` 必须以 LF 和可执行模式提交。先精确暂存它，再由维护人运行 `git update-index --chmod=+x .githooks/pre-commit` 记录可执行位；该命令只用于协作基线的文件模式，不替代其内容审阅。Windows Git 与 Linux/macOS 克隆后都需要检查钩子是否实际触发。

将真实姓名/账号对应到 A/B/C/D。需要远端强制约束时，由管理员在实际 Git 平台开启集成分支保护、禁止直接推送、必要评审及 CI。当前不知道四人的远端账号，未生成伪造的 CODEOWNERS，也未连接或修改远端权限。

## 2. 每个人拉取后的启用步骤

一人一个本机 clone，先拉取包含协作基线的代码。在 Git 根目录完成身份确认，然后显式启用。例如 B：

```powershell
python scripts/setup_collaboration.py --actor B
git switch -c feature/B/resume-parser
python scripts/check_scope.py --actor B --staged
```

A/C/D 将 B 与任务名替换为本人。上面是新建角色任务分支的示例；已有个人分支的成员不必改名，也不执行新建示例，改在自己的分支运行 `python scripts/setup_collaboration.py --actor B --branch <本人分支>`。个人分支必须已在本机存在，不能登记 `master`。

启用脚本仅在当前 clone 设置 `collab.actor`、`core.hooksPath`，提供 `--branch` 时另登记 `collab.branch`。此登记不随 pull/clone 传播，公共检查工具不预设 `master_YB` 或其他个人分支；只有登记分支与本地角色一致时才接受个人分支，仍检查路径及新增交接。原有角色任务分支继续有效，`master` 始终拒绝。有未提交改动时先辨认，不自动清理或 stash；脚本不创建分支、不提交、不推送，不改全局配置，已有其他 hooksPath 时拒绝覆盖。

这些 Git 本地设置不会随 clone/pull 自动继承，四个人必须各自运行一次。不要共用一个 clone 或混用多个角色；linked worktree 的本地配置可能共享，本版按独立 clone 使用。仓库未取得已提交的协作基线时，安装脚本会拒绝执行。

## 3. 给 Agent 的开工说明

支持 AGENTS.md 的工具应从 Git 项目根目录启动。根规则要求它显式读取更新和目标子目录规则；其他工具不支持自动读取时，将以下文本作为会话开头（B 换成本人）：

> 我是本组 B，只负责 B 工作包。先读取根 AGENTS.md、README.md、更新记录.md、tasks/B.md、模块归属表和四个角色最新交接；再显式读目标模块 AGENTS.md。确认身份/分支一致后，只修改 B 的授权路径。公共或其他模块的变化写入 docs/requests/B/，由维护人处理。结束前做范围检查、必要验证，并新增 docs/updates/B/ 交接记录。先报告计划写哪些路径。

不要假设所有工具自动识别同一套文件。CLAUDE.md 仅指向 canonical 根规则，避免维护两份正文。规则修改后重启或新建 Agent 会话，并让 Agent 复述实际读到的规则来源；旧会话不会因此自动取得新上下文。

Codex 的规则发现按启动时的目录链处理，子目录规则不等于自动扫描全仓。因此即使从根启动，修改前也须显式读取目标模块规则。依据：[OpenAI Docs](https://developers.openai.com/codex/guides/agents-md/)，查阅于 2026-11-06。

## 4. 提交、更新记录与自查

1. 检查改动，仅精确暂存本人的业务文件、必要契约与一份新增交接记录。
2. 根据 `.collaboration/UPDATE_TEMPLATE.md` 新建 `docs/updates/B/YYYYMMDD-HHMMSS-主题.md`，不修改上一次记录；需要纠正则新建关联原记录的更正记录。
3. 执行以下检查，再按团队方式提交：

```powershell
git diff --cached --name-status
python scripts/check_scope.py --actor B --staged
```

pre-commit 检查默认读取本 clone 的 collab.actor，也会校验分支角色。业务/脚本/测试变化必须带本人的新增交接记录；缺记录、其他人路径、未知路径、只读来源、敏感目录或符号链接会返回非零并阻断普通提交。规则检查不代替业务测试，也不读取身份管理平台验证“你真的是 B”。

提 PR 前还需检查已提交的整条分支：

```powershell
python scripts/check_scope.py --actor B --base origin/master
```

`origin/master` 只是示例，替换为实际集成基线；先正常 fetch 取得最新远端引用。该命令检查 `base...HEAD` 已提交差异，不包括未提交内容；暂存内容另外用 --staged。检查重命名两端、删除路径与整条分支，防止只检查最后一提交漏掉早先越界变更。

初始协作基线本身应先合入共同基线，再基于它开功能分支，否则各人比较会包含初始公共规则变更。不能把别人的 feature 分支直接作为自己的功能分支基线来绕过归属；团队合并按经审阅的各工作包进行。

## 5. 跨模块协作与冲突

Agent 不得擅自推送或合并到 `master`，包括直接推送、更新本地 `master` 的快进/合并，以及通过 PR/API 合并。执行前必须已有用户针对具体变更和 `master` 目标的明确授权；开发、修改规则、修复错误、本地提交或推送个人分支不包含这项授权。授权仅适用于指定范围，不能沿用到后续新改动或纠正任务。未获授权时保留本人分支成果，报告待集成，不自行更新 `master`。

需要公共路由/类型/依赖：在 `docs/requests/<本人>/` 用请求模板新增文件，由 A 接入；模型/任务框架请求由 D 实现。请求方不能修改对方文件；响应方在自己的更新记录关联请求，双方各自实现自己的部分。

A 负责集成，不代表 A 可以重写 B/C/D 的业务代码。公共 PR 与业务 PR 分开；冲突归相应维护人处理，不使用整文件 ours/theirs 覆盖。合并已有各角色提交是集成动作，不能假装该合并后的整条集成分支属于某一个 actor 的功能 PR。

任何人都不在 `master` 开发；规则维护同样在开发分支进行。不 force push、不 --no-verify、不改规则来消除检查错误。若合理新路径被挡，先通过请求由 A 补充归属与嵌套规则，合入后再使用。用户明确变更范围时记录其依据，不将模糊的“帮忙修一下”解释为全仓授权。

## 6. 其他人如何读取进度

根 `更新记录.md` 是 A 维护的集成索引；每个人的实际交接在 `docs/updates/A/`、`B/`、`C/`、`D/`。开工时分别查看四个目录中最新记录，并查看与当前依赖有关的更早记录。没有记录代表未交接，不代表默认完成。

交接写“已实现、已测试、未测、待联调、阻塞”及证据，不混为一个完成状态。提交 hash 可在创建后关联，记录内不预填不存在的 hash。A 汇总只链接原作者记录，不改原作者结论。

## 7. 检查工具的验证与边界

```powershell
python -m unittest discover -s tests/collaboration -v
```

该测试使用临时 Git 仓库验证自己的路径、跨角色修改、删除/移动、缺交接、追加日志、分支身份及 staged/base 检查。不会在实际项目中创建提交或开启钩子。

本地 hook 可被蓄意关闭，角色参数可被人伪报，AGENTS.md 依赖工具遵守，故不是权限沙箱；跨模块强约束仍需远端评审、可信 CI 与账号绑定。本次没有声称已启用远端防护，也未执行 push/合并。启用后应在各自 clone 做一次“故意越界应被拒绝”的本机验证。
