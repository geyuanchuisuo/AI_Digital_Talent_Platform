## 0. 结论摘要

**总体判断：架构方向合理，可以作为一期开发基线，不需要推倒重来。**

合理之处：

- 前后端分离、Controller → Service → DAO → Model 的单向分层清晰；
- SQLAlchemy 全 ORM 映射，符合“禁止裸 SQL”约束；
- LLM / Embedding / Milvus 统一放在 `core/` 适配层，业务层不直接依赖供应商 SDK；
- 没有引入 Celery、Redis、Neo4j、MinIO、Agent 编排，范围控制得较好；
- 三个功能的边界、页面清单、接口追溯矩阵基本完整；
- 长任务采用“批次 + 状态表 + 轮询”的方向正确。

但当前文档存在 **7 个会直接造成返工的结构性缺口** 和 **一组一致性问题**，主要集中在：

1. 后台任务运行模型不成立；
2. 筛选/匹配时序与异步接口自相矛盾；
3. 批次缺配置快照、唯一约束、重启恢复与幂等；
4. 解析 → 查重 → 画像状态机不闭合；
5. 需求 F1-6 的“某批次”没有数据模型支撑；
6. 匹配是否应用硬门槛未定义；
7. 评测集实际不可用。

建议：**先把本文件第 3、4、5、6 节的修改回写到五份设计文档，再进入 B1 开发**。其中 P0 项必须在 T-12、T-23、T-24、T-25 开始前完成。

## 3. P0 修改建议

### P0-1 后台任务运行模型

**现状问题**

- 架构 §5.4 写的是“上传接口写入任务后由 `BackgroundTasks` 拉起 worker”，这是按请求触发的，不是常驻队列。
- 多个上传请求会各自拉起一个 worker，虽然乐观锁能保证同一任务只被认领一次，但进程内并发数、全局 LLM 信号量、任务顺序都不受控。
- `uvicorn --workers > 1` 时每个进程都会跑 worker，任务会被重复扫描；文档没有约束部署形态。
- 解析任务有重启恢复，筛选/匹配批次完全没有恢复机制。

**建议修改**

1. 新增 `backend/app/tasks/runner.py`：
   - `TaskRunner` 单例，在 `main.py` 的 `lifespan` 启动时创建，关闭时优雅停止；
   - 主循环每 2 秒扫描三类任务：`parse_tasks`、`screen_batches`、`match_batches`；
   - 使用 `ThreadPoolExecutor(max_workers=PARSE_CONCURRENCY)` 执行解析；筛选/匹配批次按“批次 + 单人才”粒度提交；
   - 所有 LLM 调用共享一个全局信号量（默认 2），与解析/匹配并发数解耦；
   - 任务认领统一用 ORM Core `update(...).where(status='pending')`，按 `rowcount` 判断是否抢到；
   - 记录 `started_at`、`heartbeat_at`，启动时把 `running` 且超过 10 分钟未心跳的任务重置为 `pending`（三类任务都做）；
   - 退出时等待当前任务完成或标记回 `pending`，避免“进程被杀任务永远 running”。

2. 部署约束写入运行手册：一期只允许 `uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1`；如果以后要多进程，必须把 worker 拆成独立进程（二期）。

3. 健康检查增加 `worker` 状态：最近心跳时间、当前并发数、队列积压数。

**涉及文档**

- 架构 §5.4 重写；§2 总体架构图把 `BG` 改为 `TaskRunner`；
- 架构 §6.1/§6.2/§6.3 的时序图改成“HTTP 只创建批次，worker 异步执行”；
- 计划 T-12 增加“常驻 runner + 三类任务恢复”；T-24/T-25 增加批次认领与恢复；
- 接口 §10.3 保留“LLM 只在后台任务中调用”，补充“单进程部署约束”。

**验收点**

- 连续发起 2 次上传，只有一个 runner 在跑，任务不重复；
- 解析/筛选/匹配运行中杀掉服务并重启，任务自动恢复或明确失败可重试；
- 同一批次重试后不产生重复结果。

### P0-2 筛选/匹配时序修正

**现状问题**

架构 §6.2 的时序是：

```text
FE -> API POST /screen/batches
API -> SVC 创建批次 + 逐人任务
loop 每份简历：硬门槛 -> LLM 评分 -> 归档
FE -> API GET 批次（轮询）
```

这等于在 POST 请求内完成全部评分，与接口设计的“HTTP 202 + 后台执行 + 前端轮询”直接冲突，也无法满足普通接口 ≤2s。

**建议修改**

把 §6.2 改成两段时序：

1. **创建批次（同步，≤2s）**：校验岗位条件、圈定人才范围、写 `screen_batches(pending)`，返回 `batch_id/total/status`，HTTP 202；
2. **worker 执行（异步）**：认领批次 → 逐人执行 `match_engine` → 写 `screen_results` → 更新 `progress` → 完成后置 `done`；失败置 `failed` 并记录 `error`。

匹配 §6.3 同理：POST 只创建 `match_batches`，worker 逐人评分，done 后回填名次或查询时计算名次。

**涉及文档**

- 架构 §6.2、§6.3；
- 接口 §7、§8 补充“worker 执行”说明；
- 计划 T-24/T-25 明确“接口只创建批次，评分在 worker”。

**验收点**

- POST 批次接口在 2s 内返回；
- LLM 调用只出现在 worker 日志中；
- 轮询能看到 `progress` 从 0 到 total。

### P0-3 批次一致性、幂等与恢复

**现状问题**

- `screen_batches`/`match_batches` 只存 `job_profile_id`，岗位条件被 PUT 修改后，运行中批次和历史结果都无法复现；
- `screen_results`/`match_results` 没有 `(batch_id, talent_profile_id)` 唯一约束，重试/重启可能写重复行；
- 批次没有认领字段和恢复机制；
- `match_results.rank` 在 done 后统一回填，失败批次会留空；
- 没有批次重试接口。

**建议修改**

1. `job_profiles` 增加 `version INT NOT NULL DEFAULT 1`；每次 PUT 成功更新时 `version = version + 1`。
2. `screen_batches`/`match_batches` 增加：
   - `job_profile_version INT NOT NULL`；
   - `config_snapshot_json JSON NOT NULL`：岗位标题、部门、JD、任职要求、最低学历、最低年限、必备/加分技能、硬门槛开关、阈值、权重；
   - `started_at DATETIME NULL`、`heartbeat_at DATETIME NULL`；
   - `error TEXT NULL`；
   - `retry_of_batch_id BIGINT UNSIGNED NULL`。
3. 结果表增加唯一约束：
   - `uk_screen_batch_talent (screen_batch_id, talent_profile_id)`；
   - `uk_match_batch_talent (match_batch_id, talent_profile_id)`。
4. 重试策略：
   - `POST /screen/batches/{id}/retry`、`POST /match/batches/{id}/retry`；
   - 仅 `failed` 可重试；创建新批次并写 `retry_of_batch_id`，或复用原批次重置状态；
   - 复用原批次时，worker 按唯一键跳过已有结果，只补算缺失项；
   - 批次完成后按结果表重新统计 passed/pending/rejected/hard_failed，避免计数漂移。
5. 名次：
   - 推荐查询时计算：`rank = 分页 offset + 行号`，按 `score DESC, id ASC`；
   - 如需持久化 `rank`，只在批次 `done` 后一次性回填，失败批次保持 NULL 并在接口返回时按分数临时计算。

**涉及文档**

- 数据库 §6.1-§6.5；
- 接口 §7/§8 增加 retry 接口与字段；
- 计划 T-24/T-25。

**验收点**

- 批次运行中修改岗位条件，本批次结果不变；
- 同一批次重复执行/重试，结果行数不变；
- 失败批次重试后补齐结果，计数与结果表一致。

### P0-4 解析 → 查重 → 画像状态机

**现状问题**

- 架构 §6.1 时序先“查重”，再在“新人才”分支写 `parsed_resumes`；但 `talent_duplicates.parsed_resume_id` 是非空字段，查重记录必须先有 `parsed_resumes`。
- 画像生成包含 LLM 标签/能力评分 + Embedding + Milvus upsert；任何一步失败，解析任务可能已经被标记 `success`，出现“有解析无画像”。
- `parse_tasks.status` 已有 `duplicate_pending`，但它混合了“解析状态”和“查重状态”；队列展示和恢复逻辑不清晰。
- 查重原因包含 `hash_match`，但文件哈希在**上传阶段**已经去重，内容哈希重复的简历不会进入解析，`hash_match` 实际不可达。

**建议修改**

1. 明确流水线顺序：

```text
上传 → parse_tasks(pending)
worker 认领 → 提取文本 → LLM 结构化提取
→ 写 parsed_resumes（talent_profile_id = NULL）
→ 查重（规范化 phone/email + 姓名）
→ 新人才：创建 talent_profiles → LLM 标签/能力 → 拼画像文本 → Embedding → Milvus upsert
→ 成功
疑似重复：写 talent_duplicates(pending)，parse_task 置 duplicate_pending，不创建画像
任一步失败：parse_task 置 failed，记录 stage/error，可重试
```

2. `parse_tasks` 调整：
   - 增加 `stage VARCHAR(20) NULL`：`extract` / `profile` / `vector`；
   - 增加 `profiled_at DATETIME NULL`；
   - 增加唯一约束 `uk_resume_file (resume_file_id)`，与“1:1 当前任务”一致；
   - `status` 取值固定为 `pending/running/success/failed/duplicate_pending`；
   - 重试时重置 `status=pending`、`stage=NULL`、`error=NULL`，`retries` 保留累加。

3. 查重规则：
   - 上传阶段：文件 SHA-256 重复 → 跳过并提示，不创建 `resume_files`/`parse_tasks`；
   - 人才阶段：规范化后手机号相等，或邮箱相等，或“姓名 + 手机号”相等；
   - 姓名单独相等不作为查重依据，避免同名误合并；
   - `talent_duplicates.reason` 只保留 `phone_match/email_match/name_phone_match`，删除 `hash_match`。

4. 合并语义：
   - master 选择：默认最早创建的画像，HR 可在确认时指定；
   - 合并字段：人工修正优先，其次较新简历的非空值；标签取并集；`skills` 取并集；
   - `parsed_resumes.talent_profile_id` 改指 master；
   - profile_b 软删除（见 P1-3），Milvus 向量重算；
   - 记录 `resolved_by/resolved_at`。

5. `POST /talents/duplicates/{id}/resolve`：
   - `merge` 可同步完成（只做 DB 关联 + 向量重算，LLM 标签不重跑，标签取并集）；
   - `keep` 需要创建新画像并生成标签/能力/向量，建议返回 202 + 后台任务，避免接口超过 2s。

**涉及文档**

- 架构 §6.1 时序重画；
- 数据库 §4.2/§4.3/§5.2；
- 接口 §5 查重接口；
- 计划 T-12/T-14/T-16/T-17 的顺序与依赖。

**验收点**

- 标签 LLM 失败后任务为 `failed(stage=profile)`，重试后成功；
- 重复简历触发 `talent_duplicates`，解析任务为 `duplicate_pending`，不创建画像；
- 合并后只剩一个画像，`parsed_resumes` 全部指向 master，向量已重算。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT UNSIGNED | PK, AI | |
| cache_key | CHAR(64) | NOT NULL, UNIQUE | SHA-256 |
| scene | VARCHAR(30) | NOT NULL | screen / match / parse / profile |
| job_profile_id | BIGINT UNSIGNED | NULL, IDX | 解析/画像场景为 NULL |
| job_profile_version | INT | NULL | 岗位版本 |
| talent_profile_id | BIGINT UNSIGNED | NULL, IDX | |
| profile_text_hash | CHAR(64) | NULL | 画像文本哈希 |
| prompt_version | VARCHAR(30) | NOT NULL | 提示词版本 |
| model | VARCHAR(100) | NOT NULL | LLM 模型名 |
| output_json | JSON | NOT NULL | 评分/标签/理由结果 |
| created_at | DATETIME | | |

`cache_key` 建议公式：

```text
SHA256(scene | job_profile_id | job_profile_version | profile_text_hash
       | prompt_version | model | normalized_weights_or_thresholds)
```

说明：

- 岗位配置变化 → `version` 变化 → cache miss；
- 画像文本变化 → `profile_text_hash` 变化 → cache miss；
- 换模型/改提示词 → cache miss；
- 缓存只用于评分/标签等“可重复计算”的结果，不缓存文件文本；
- 评测运行使用独立前缀或关闭缓存，避免“缓存命中”掩盖模型退化。

### 4.5 JSON 字段注意事项

SQLAlchemy 的 `JSON` 字段默认不会检测原地修改。所有 `tags_json`、`ability_scores_json`、`weights_json`、`hits_json`、`config_snapshot_json` 的更新必须：

- 重新赋值（`obj.tags_json = new_list`），或
- 使用 `MutableList`/`MutableDict` 包装。

否则会出现“接口返回成功但数据库没变”的隐蔽 bug。

- 时间统一 ISO 8601，带时区或明确 `Asia/Shanghai` 约定。

## 6. 判定与评分规则（建议）

这一节是 P0-4/P0-6 的配套规则，建议写入架构或单独《算法与判定规则.md》，否则不同开发人员实现出的硬门槛结果会不一致。

### 6.1 学历归一化

| 归一化值 | 可接受原文示例 | 排序 |
|---|---|---|
| 博士 | 博士、博士研究生、PhD | 5 |
| 硕士 | 硕士、研究生、MBA、Master | 4 |
| 本科 | 本科、大学本科、学士、Bachelor | 3 |
| 大专 | 大专、专科、高职 | 2 |
| 高中/中专 | 高中、中专、职高 | 1 |
| 其他 | 无法识别 | 0 |

硬门槛比较用排序值，不直接比较字符串。

### 6.2 工作年限

- 优先用 `employments` 的起止时间计算；
- 合并重叠区间，避免同一段时间重复累计；
- 进行中的经历结束时间按“当前日期”计算；
- 结果保留 1 位小数；
- 若 LLM 未给出结构化经历但给出 `work_years`，以 `work_years` 兜底；
- 若硬门槛开启且年限完全缺失，判为不达标，原因写“工作年限缺失”，允许人工改判。

### 6.3 必备技能

- 归一化：去空格、英文小写、全角转半角；
- 别名表可配置，例如 `Go/Golang`、`React/React.js`、`Spring Boot/SpringBoot`；
- `must_skills` 中任意一项未命中 → 硬淘汰，原因列出缺失项；
- 技能列表为空且开关开启 → 硬淘汰；
- 加分技能只进入命中项/理由，不参与硬淘汰。

### 6.4 匹配分数

建议公式：

```text
base = skills * w_skills + experience * w_experience
     + education * w_education + others * w_others
experience = 0.7 * llm_experience + 0.3 * (vector_similarity * 100)
```

- 四个维度由 LLM 给出 0–100 分，并附命中/缺失；
- 向量相似度只嵌入“经历相关性”维度，避免与四维权重重复计算；
- 权重来自批次快照，总和必须为 100；
- `hard_fail=1` 时最终 `score=0`，不参与正常排名；
- 分数保留 1–2 位小数，展示时四舍五入；
- `temperature=0`，同一输入 + 同一版本应得到稳定结果；缓存命中时直接复用。

如果希望向量相似度独立成第五维，需要把 `weights_json` 改为五维并重新定义总和；建议一期不做，保持四维 + 向量嵌入经历维度。

### 6.5 筛选阈值

- `pass_threshold` 默认 75，`pending_threshold` 默认 60；
- 校验 `pass_threshold > pending_threshold`；
- `score >= pass_threshold` → passed；
- `pending_threshold <= score < pass_threshold` → pending；
- `score < pending_threshold` → rejected；
- 硬淘汰 → rejected，`score=NULL` 或 0（筛选结果表保持 `score=NULL`，匹配结果表用 0，二者在文档中明确）；
- 通过率 = passed / total（total 包含硬淘汰），文档写明口径。

### 6.6 标签与能力评分

- 标签数量 10–30；少于 10 个时重试 1 次，仍不足则接受但记录 warning；
- 能力五维：专业技能、项目经验、教育背景、稳定性、成长潜力；每维 0–100 + 一句话依据；
- 超出范围的分值 clamp 到 0–100；
- 标签/能力输出失败不得阻断解析任务成功，但必须标记 `failed(stage=profile)` 并可重试；建议不要让“画像失败”产生半成品画像。

## 8. 测试与验收调整

### 8.1 验收标准补充

在需求第 9 节基础上增加：

1. **任务恢复**：解析/筛选/匹配运行中重启服务，任务恢复或明确失败可重试；
2. **批次幂等**：同一批次重试/重复执行，结果不重复；
3. **配置快照**：批次运行中修改岗位条件，本批次结果不变；

5. **上传批次**：只筛选指定上传批次的简历；
6. **标签过滤**：按标签/标签类型精确过滤，结果与画像一致；
7. **软删除**：删除画像后列表不可见、历史结果仍显示姓名；

9. **Milvus 降级**：Milvus 停止时语义检索返回 503，解析/普通 CRUD 不受影响；
