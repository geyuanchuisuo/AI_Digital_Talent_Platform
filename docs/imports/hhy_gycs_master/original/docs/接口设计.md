## 1. 全局约定

### 1.1 统一返回
```json
{ "code": 0, "message": "success", "data": { } }
```
列表类 data：`{ "items": [...], "total": 100, "page": 1, "page_size": 20 }`
批次创建类接口返回 **HTTP 202**（body 仍为统一格式）。
错误响应额外带 `request_id`；成功 / 202 **不带**：`{ "code": 400, "message": "...", "data": null, "request_id": "req-..." }`
**唯一例外**：`GET /health` 直接返回 §3 的健康检查结构，不套 `code/message/data`。

### 1.2 错误码
| code | HTTP | 含义 |
|---|---|---|
| 0 | 200/202 | 成功 |
| 400 | 400 | 参数/业务校验失败（权重总和≠100、pass≤pending、批次范围无对象、状态不可重试等） |
| 401 | 401 | 未认证 / token 失效 |
| 403 | 403 | 账号停用（is_active=0） |
| 404 | 404 | 资源不存在（含重复 DELETE，幂等口径统一 404） |
| 409 | 409 | 冲突（唯一键类；文件重复不在此列，见 §4） |
| 422 | 422 | Pydantic 结构校验失败 |
| 500 | 500 | 服务内部错误 |
| 503 | 503 | 依赖不可用（LLM / Embedding / Milvus）——**仅用于「请求尚未产生任何业务写入」的场景**（典型：语义检索）。MySQL 已提交后向量失败**不返回 503**，见下方半写口径 |

错误体：`{"code": 400, "message": "weights 总和必须为 100", "data": null, "request_id": "..."}`

**半写口径（决策 D-B，与《架构设计》§5.1 一致）**：同步接口（`PATCH /talents/{id}`、duplicates `merge`、`restore`、`revector`）在 **MySQL 事务已提交**后，若 embedding 或 Milvus upsert 失败/超过 `VECTOR_SYNC_TIMEOUT`（默认 5s，运行配置 v1.4；原 1.5s 因冷连接 embedding ~1.7s 误判超时上调），一律返回 **HTTP 200**，`data.vector_status="failed"`，`message` 提示「画像已保存，向量同步失败，可稍后重试」；**不回滚业务数据、不返回 503**。补偿入口：`POST /talents/{id}/revector`。

### 1.3 通用规则
- 鉴权：除 `POST /auth/login`、`GET /health` 外全部接口需 `Authorization: Bearer <JWT>`；停用账号 403。
- 分页：`page`（默认 1）、`page_size`（默认 20，上限 200）。
- 时间：ISO 8601，Asia/Shanghai 口径。
- 长任务：POST 创建批次 → 202 + batch_id → **常驻 TaskRunner 异步执行** → 前端 2s 轮询批次详情（status/progress），done/failed 停止。
- 分数单位：`score`、四维 `dimension_scores` 为 0–100；`vector_similarity` 单独 0–1；`hits/misses` 为字符串数组。
- 文件上传：`multipart/form-data`，字段 `files`（可多个）。

## 3. 系统 `health`

### GET /health（免鉴权，快速返回，**不主动调用** LLM/Embedding）
```json
{
  "status": "ok",
  "db": true,
  "milvus": true,
  "milvus_version": "2.6.x",
  "llm_configured": true,
  "embedding_configured": true,
  "embedding_alive": true,
  "worker": {"alive": true, "last_heartbeat": "...", "concurrency": 2, "backlog": {"parse": 3, "screen": 1, "match": 0, "duplicate_pending": 1, "cancelled": 0}},
  "version": "0.1.0"
}
```
- 任一依赖异常 → `status: "degraded"`，**HTTP 仍 200**。
- `concurrency` 取 `sys_settings.task_concurrency` 当前值（**不是** `.env`，见 §4 `PATCH queue/settings`）。
- `embedding_alive`：**被动探活**——反映最近一次真实 embedding 调用是否成功（进程内缓存，从未调用过则为 `null`）。这样既能暴露「Embedding 单独不可用（Milvus 正常）」，又不违反「health 不主动调用 Embedding」的约束。
- `milvus` 为轻量连通性检查（连接 + collection 存在性），不做检索。

## 4. 简历与解析队列 `resumes`（F1-1 ~ F1-5）

### POST /resumes/batch
请求：multipart，`files` 多个（pdf/docx，单文件 ≤20MB；扩展名 + magic bytes 校验）。
行为：生成 `upload_batch_id`（ULID）→ 逐文件 SHA-256；已存在哈希**跳过计入 duplicates（不报错）**；新文件重命名存储 + 写 `resume_files` + `parse_tasks(pending)`。TaskRunner 自动拉起，无需接口触发。
> **注意（决策 D-M）**：`upload_batch_id` 只是 `resume_files` 上的字段，**不存在 `upload_batches` 表**；批次信息一律实时聚合，不落批次实体（数据库 §4.1）。
> **注意（H-13，不是缺陷）**：`filename` 按 multipart 原样保存（浏览器/TestClient 为 UTF-8）。用 Git Bash 的 `curl -F "files=@张三.pdf"` 可能显示成 `ÕÅÈý...pdf`，那是 curl 按 GBK 发字节导致的，**不要为此在服务端加编码猜测转码**（会转坏西欧文件名）；验证中文名请用浏览器或 pytest/TestClient。
> **注意（决策 D-H）**：`resume_files` 行**永不物理删除**（审计与原文下载需要），所以同一份文件重传**永远**落入 `duplicates`，不会自动重新入队。要重跑请用响应里的 `task_id` 调 `POST /resumes/queue/{task_id}/requeue`。
响应 data（**HTTP 202**）：
```json
{
  "upload_batch_id": "01JABCDEFGHJKMNPQRSTVWXYZA",
  "accepted": 8,
  "duplicates": [{"filename": "张三.pdf", "reason": "文件内容已存在", "resume_file_id": 9, "task_id": 12, "task_status": "failed", "can_requeue": true}],
  "rejected": [{"filename": "简历.exe", "reason": "非法文件类型"}],
  "queue_total": 8
}
```
- `can_requeue`：已存在任务处于 `cancelled` / `failed` 时为 `true`（前端展示「重新入队」按钮）；`pending`/`running`/`success`/`duplicate_pending` 为 `false`。
- 错误：400 无任何有效文件（全部非法/超限，逐项列明原因）。**全部命中 duplicates 不算错误**，仍返回 202（`accepted=0`）。

### GET /resumes/batches （上传批次汇总，供筛选范围下拉）
Query：分页。响应 items：
```json
{"upload_batch_id": "01J...", "file_count": 8, "success": 6, "failed": 1, "pending": 1, "uploaded_at": "..."}
```
> 数据来源：`resume_files GROUP BY upload_batch_id`（`uploaded_at = MIN(created_at)`，`total` = 去重批次数）。**没有 `upload_batches` 表**（决策 D-M），新增/删除批次无需同步第二张表。

### GET /resumes/queue
Query：`status`（含 `cancelled`）、`upload_batch_id`、`page`、`page_size`
响应 data：
```json
{
  "summary": {"pending": 3, "running": 2, "success": 10, "failed": 1, "duplicate_pending": 1, "cancelled": 0, "total": 17},
  "concurrency": 2,
  "items": [{"task_id": 1, "resume_file_id": 9, "filename": "张三.pdf", "upload_batch_id": "01J...", "status": "failed", "stage": "vector", "retries": 1, "error": "Milvus 连接失败: ...", "truncated": false, "created_at": "...", "started_at": "...", "finished_at": "...", "profiled_at": null, "talent_profile_id": 5, "can_retry": true, "can_requeue": false}],
  "total": 17, "page": 1, "page_size": 20
}
```
- `concurrency` 取 `sys_settings.task_concurrency`；`can_retry`（`failed` 为 true）/`can_requeue`（`cancelled` 或 `failed` 为 true）供前端控制按钮。

### PATCH /resumes/queue/settings
请求：`{"concurrency": 3}`（int，**1–5**，越界 400）。响应 data：`{"concurrency": 3, "effective": "next_scan"}`。
行为（决策 D-C）：写入 **`sys_settings.task_concurrency`**（持久化，重启保持）；TaskRunner 每个扫描周期（2s）读取一次，在**无在跑任务时重建线程池**，因此最迟一个周期内生效（`effective:"next_scan"`）。该并发是 **TaskRunner 全局任务并发**（解析/筛选/匹配共用一个池），不是"仅解析并发"。

### POST /resumes/queue/{task_id}/retry
仅 `failed` 可重试。**断点续跑**：置 `status='pending'`、`error=NULL`、`retries += 1`，**保留 `stage`** 作为续跑起点（`stage='vector'` 只补 embedding+upsert，不重跑 LLM；`stage='profile'` 且 `talent_profile_id` 已回填则跳过查重与建画像）。`started_at/heartbeat_at/finished_at` 置 NULL。错误：400 状态不可重试；404 不存在。

### POST /resumes/queue/{task_id}/requeue （v1.2 新增，决策 D-H）
适用 `cancelled` 与 `failed`：置 `status='pending'`、**`stage=NULL`（从头重跑）**、`error=NULL`、`retries += 1`。与 `retry` 的区别是**不保留 stage**。因 `parse_tasks` 与 `resume_files` 恒 1:1 且 `cancelled` 不删行，本接口不插入新行、不会撞 `uk_resume_file`。错误：400 状态不可重新入队（`pending`/`running`/`success`/`duplicate_pending`）；404 不存在。

### DELETE /resumes/queue/{task_id}
**软取消**：置 `status='cancelled'`（不物理删行）；`pending`/`failed`/`success`/`duplicate_pending` 可删，`running` 拒绝（400）。**文件与画像不连带删除**（原文仍可下载、画像仍在库）。已是 `cancelled` 再删 → **404**（活动队列中已不存在）。恢复入口：`requeue`。

## 5. 人才画像 `talents`（F2）

### GET /talents
Query：`keyword`（姓名/职位/技能模糊）、`tag`（**精确匹配，走 talent_tags**）、`tag_type`、`degree`、`min_years`、`max_years`、**`deleted`（v1.2 新增：`false` 默认只看未删除；`true` **回收站视角**，只返回已软删除画像，供 `restore` 选取）**、`page`、`page_size`
行为：默认排除 `deleted_at IS NOT NULL`；`deleted=true` 时反向只取已软删除项并按 `deleted_at DESC` 排序；标签过滤 join `talent_tags`。
items 元素：
```json
{"id": 5, "name": "张三", "current_title": "后端工程师", "work_years": 4.0, "degree": "本科", "city": "深圳", "tags": ["python", "fastapi", "..."], "tag_total": 18, "source": "resume", "manual_edited_fields": ["phone"], "vector_status": "synced", "deleted_at": null, "updated_at": "..."}
```
说明：tags 仅返回前 8 个；排序默认 `updated_at DESC`；列表查询用预加载防 N+1；**`deleted_at` 字段两种视角都返回**（回收站视角据此显示删除时间）。

### GET /talents/search （语义检索，F2-5）
Query：`query`（必填 ≤500 字）、`top_k`（默认 20，上限 100）
行为：query → embedding（**相同查询文本短期缓存**）→ Milvus COSINE topK → 回查 MySQL（排除软删除）。
items：画像摘要 + `"similarity": 0.83`。错误：503 Milvus/Embedding 不可用。
注意路由注册在 `/talents/{id}` **之前**。

### GET /talents/{id}
响应 data：
```json
{
  "profile": {"id": 5, "name": "张三", "gender": "男", "birth_year": 1996, "phone": "13800000000", "email": "z@x.com", "city": "深圳", "degree": "本科", "work_years": 4.0, "current_title": "后端工程师", "expected_title": "高级后端", "skills": ["python", "..."], "tags": [{"tag": "python", "tag_type": "skill", "source": "llm"}], "ability_scores": {"professional": {"score": 85, "basis": "…"}, "project_experience": {"score": 78, "basis": "…"}, "education": {"score": 70, "basis": "…"}, "stability": {"score": 88, "basis": "…"}, "growth_potential": {"score": 80, "basis": "…"}}, "manual_edited_fields": ["phone"], "vector_status": "synced", "created_at": "...", "updated_at": "..."},
  "educations": [...], "employments": [...], "projects": [...], "certificates": [...],
  "resume_files": [{"resume_file_id": 9, "filename": "张三.pdf", "upload_batch_id": "01J..."}],
  "screen_history": [{"batch_id": 2, "job_title": "高级后端工程师", "effective_verdict": "passed", "score": 82.5, "created_at": "..."}],
  "match_history": [{"batch_id": 1, "job_title": "高级后端工程师", "score": 86.0, "hard_fail": false, "created_at": "..."}]

```
说明：详情内手机号/邮箱完整返回（业务需要），日志层脱敏；已软删除画像返回 404（历史结果 join 时仍显示姓名）。`educations/employments/projects/certificates` 是该画像关联的全部 `parsed_resumes` 聚合后的只读视图，按数据库 §5.3 第 4 条去重（`company + title + start`，保留 `end` 较晚、其次 `description` 更长）。

### PATCH /talents/{id} （人工修正，F2-6 字段级保护）
请求：任意可修正字段子集（name/phone/email/city/degree/work_years/current_title/expected_title/skills/tags/ability_scores）。`degree` 必须是归一化枚举字面值（`博士/硕士/本科/大专/高中中专/其他`，否则 400）。
**不可修改**：`educations/employments/projects/certificates` 为一期只读，请求里出现这些键按 400 处理；它们由 `parsed_resumes.structured_json` 按 `talent_profile_id` 聚合展示（数据库 §5.3），画像表没有独立存储位。
行为：
1. **仅将本次实际修改的字段并入 `manual_edited_fields`**；写 `updated_by`；
2. tags/skills 变更 → **同一事务**内重建 `talent_tags` 并刷新 `tags_json`（`source='manual'` 不被覆盖为 `llm`）；
3. **向量重算按 hash 触发，不按字段类型判断**：提交后重算画像文本 → 与 `profile_text_hash` 比对 → **变了才** embedding + Milvus upsert 并更新 `vector_status/vector_synced_at`。因此改 city/degree/name/current_title/expected_title/work_years 同样会刷新向量（这些字段都在画像文本里，《算法与判定规则》§6.3）；
4. 向量步骤受 `VECTOR_SYNC_TIMEOUT`（5s，v1.4）约束；失败或超时 → **HTTP 200** + `vector_status:"failed"`（§1.2 半写口径），业务字段已保存不回滚。
响应 data：`{"profile": {...更新后}, "manual_edited_fields": ["phone", "tags"], "vector_status": "synced", "profile_text_changed": true}`
错误：404 不存在或已软删（软删画像需先 `restore`）；400 枚举/类型非法。

### POST /talents/{id}/restore （v1.2 新增，决策 D-H）
行为：`deleted_at/deleted_by` 置 NULL；按 `profile_text_hash` 重新 embedding + Milvus upsert（向量原本随软删被删除）；同样适用半写口径。恢复后画像重新进入 `all/filter` 圈定范围，历史筛选/匹配结果自动可点开详情。
响应 data：`{"restored": true, "vector_status": "synced"}`。错误：400 未被软删；404 不存在。

### POST /talents/{id}/revector （v1.2 新增，向量补偿）
行为：只重算画像文本 → embedding → upsert，**不触碰任何业务字段**；用于修 `vector_status='failed'`。全量补偿用 `scripts/rebuild_vectors.py`。
响应 data：`{"vector_status": "synced", "vector_synced_at": "..."}`。错误：404 不存在；**Milvus/Embedding 不可用 → 503**（本接口无业务写入，符合 §1.2 的 503 边界）。

### DELETE /talents/{id} （软删除，F2-7）
行为：写 `deleted_at/deleted_by`；删除 Milvus 向量；关联 `parsed_resumes.talent_profile_id` 保留（历史可溯）；原始文件保留；历史筛选/匹配结果保留（列表 join 显示姓名 + "已删除"标记）。重复删除 404。
- Milvus 删除失败时 **MySQL 软删仍生效，返回 200** + `"vector_deleted": false`；残留向量无害（语义检索会回查 MySQL 排除软删画像），由 `rebuild_vectors.py` 清理。
- **恢复入口**：`POST /talents/{id}/restore`（见上）。
响应 data：`{"deleted": true, "vector_deleted": true}`

### GET /talents/{id}/resume-file?resume_file_id=9
响应：文件流（`application/octet-stream`，Content-Disposition 原始文件名，路径穿越防护）。
**前端必须用 axios `responseType: 'blob'` 携带 Bearer 下载**（`<a href>` 直链无法带 Header 会 401），拿到 blob 后触发保存。

### GET /talents/duplicates
Query：`status`（默认 pending）、分页。注意注册在 `/talents/{id}` 之前。
items：
```json
{"id": 1, "reason": "phone_match", "matched_value": "138****0000", "status": "pending", "profile_a": {"id": 5, "name": "张三", "current_title": "后端工程师", "created_at": "..."}, "profile_b": null, "parsed_resume": {"id": 12, "filename": "张三-新版.pdf", "name": "张三", "phone": "138****0000"}, "created_at": "..."}
```

### POST /talents/duplicates/{id}/resolve
请求：`{"action": "merge", "master_profile_id": 5}`（**可省略，默认且只能是 `profile_a_id`**）或 `{"action": "keep"}`，可选 `resolution_note`。

**`merge`（同步，≤2s，详见《数据库设计》§5.3.1）**
1. `master_profile_id` 省略 → 取 `profile_a_id`；显式传值但 ≠ `profile_a_id` → **400**（`pending` 阶段 `profile_b_id` 为 NULL，不存在第二个候选，原「HR 可任意指定 master」的口径作废）。
2. 标量字段合并：master 的 `manual_edited_fields` 所列字段保持不变，其余按「新解析结果非空值覆盖」。
3. **`ability_scores_json` 保留 master 原值**，不重算、不取新值（合并阶段不重跑 LLM）。
4. tags/skills 取并集（归一化，事务内重建 `talent_tags`，`source='manual'` 不被覆盖）。
5. 相关 `parsed_resumes.talent_profile_id` 全部改指 master（详情页据此聚合多份简历经历，展示层按 `company+title+start` 去重）。
6. 画像文本重算 → hash 变化 → embedding + Milvus upsert（受 `VECTOR_SYNC_TIMEOUT` 5s 约束，v1.4）。
7. 同一事务收尾：`talent_duplicates.status='merged'` + `resolved_by/resolved_at`；对应 `parse_tasks` → `status='success'`、`stage=NULL`、**`profiled_at/finished_at=NOW()`**。
8. 向量失败 → **200** + `vector_status:"failed"`（半写口径，不回滚合并）。
响应 200：`{"duplicate_id": 1, "status": "merged", "master_profile_id": 5, "profile": {...合并后摘要}, "vector_status": "synced", "task_id": 12, "task_status": "success"}`

**`keep`（202 异步，详见《数据库设计》§5.3.2）**
1. **同步阶段**（所以能返回 `talent_profile_id`）：为新解析结果创建独立画像行——`source='resume'`、标量字段取自 `parsed_resume.structured_json`（学历/年限/技能已归一化）、`tags_json/ability_scores_json` 暂为 NULL、`vector_status='pending'`；同事务回填 `parsed_resumes.talent_profile_id`、`talent_duplicates.profile_b_id` 与 `status='kept'`、`resolved_by/resolved_at`；并把 `parse_tasks` 置 **`status='pending'` + `stage='profile'`**。
2. **异步阶段**：TaskRunner 下一轮扫描按断点续跑从 `stage=profile` 补 LLM 标签（10–30）+ 能力五维 + 画像文本 + embedding + upsert；成功写 `profiled_at/finished_at` 与 `status='success'`。
3. **失败可见可重试**：后台失败落 `parse_tasks.failed(stage='profile'|'vector', error)`，在解析队列正常展示并可 `retry`。
响应 **202**：`{"duplicate_id": 1, "status": "kept", "talent_profile_id": 20, "task_id": 12, "task_status": "pending", "stage": "profile"}`；进度经 `GET /resumes/queue`（按 `upload_batch_id`/`resume_file_id` 过滤）呈现。

错误：400 记录已处理（`status != 'pending'`）或 `master_profile_id` 非法；404 不存在。

请求：
```json
{
  "title": "高级后端工程师", "department": "技术部",
  "jd_text": "…", "requirements_text": "…",
```

### DELETE /job-profiles/{id}

## 7. 简历筛选 `screen`（F1-6 ~ F1-12）

### POST /screen/batches
请求：
```json
{"job_profile_id": 1, "scope": {"type": "upload_batch", "upload_batch_id": "01J..."}}
```
scope 四种（语义见附录 B）：`all_unscreened` / `upload_batch` / `resume_file_ids`（`{"ids":[9,10]}`）/ `all`。
行为（同步，≤2s）：
1. 校验岗位有效（停用 → 400）；
2. 按 scope 圈定"解析成功且已有画像"的人才集合，得到**确定的 `talent_profile_id` 清单**；
3. 写 `screen_batches(pending, job_profile_version, config_snapshot_json, scope_json{...原始条件, resolved_ids:[...]}, total=len(resolved_ids))`；
4. TaskRunner 异步执行，**worker 与 retry 一律只按 `resolved_ids` 快照执行，不重新圈人**（决策 D-D）——因此创建时仍在解析的简历不会被补进本批，retry 前新增的画像也不会被补进来。
响应 data（**202**）：`{"batch_id": 3, "total": 12, "status": "pending", "estimated_llm_calls": 10}`
- `estimated_llm_calls`：`resolved_ids` 中**通过硬性门槛预检**的人数（预检只跑规则层、不调 LLM，因此可在 2s 内完成）；硬淘汰者不计入。
- 错误：400 范围内无可筛选对象（`resolved_ids` 为空）/ 岗位停用。

### GET /screen/batches
Query：`job_profile_id`、分页。items：`{batch_id, job_title, job_profile_version, status, progress, total, passed, pending_count, rejected, retry_count, created_at, finished_at}`

### GET /screen/batches/{id} （轮询）
响应 data：批次详情 + `config_snapshot` 摘要 + `error` + 三档计数 + `scope`（原始条件，不含 `resolved_ids` 全量，只返回其长度）+ `processed`（已写结果行数）+ `skipped_deleted`（快照内被软删而跳过的人数）+ `vector_degraded`（**筛选批次恒为 `false`**，见《算法与判定规则》§4.0）。
- `progress` 与 `total` 可能不等（快照内画像被软删时跳过），前端展示 `progress / total` 并在 `skipped_deleted > 0` 时给出提示。

### POST /screen/batches/{id}/retry
仅 `failed` 可重试。**统一为「复用原批次」语义（决策 D-E，原「如创建新批次方式则回填」的二义表述作废）**：
- 复位：`status='pending'`、`error=NULL`、`started_at=NULL`、`heartbeat_at=NULL`、`finished_at=NULL`、`vector_degraded=0`、**`retry_count += 1`**；
- **保持不变**：`config_snapshot_json`、`job_profile_version`、`scope_json.resolved_ids`、`total`、已写入的 `screen_results` 行；
- `progress` 按已有 `screen_results` **行数重算**（不清零）；
- worker 依 `uk_screen_batch_talent` 只补缺失项 → **重试后结果行数不增不减**（T-24 验收点）。
- **快照语义**：本批次结果 = 执行时快照。retry 只补缺、不重跑已写成员——即使 retry 前画像被人工修改过，已写的那条结果分数不变。想让修改生效请**另建批次**。
- 错误：400 状态不可重试（仅 `failed` 允许）；404 不存在。

### GET /screen/batches/{id}/results
Query：`verdict`（按**有效结论** manual_verdict??verdict 过滤）、`keyword`、分页；排序 score DESC（硬淘汰置底）。
items：
```json
{"result_id": 30, "talent_profile_id": 5, "name": "张三", "current_title": "后端工程师", "degree": "本科", "work_years": 4.0, "hard_fail": false, "hard_fail_reason": null, "score": 82.5, "verdict": "passed", "manual_verdict": null, "effective_verdict": "passed", "manual_verdict_by": null, "manual_verdict_at": null, "reason_summary": "命中 python/fastapi…", "hits": ["Python", "FastAPI"], "misses": ["Milvus"]}
```

### PATCH /screen/results/{result_id} （人工改判，F1-10）
请求：`{"manual_verdict": "passed"}` 或 `{"manual_verdict": null}`（撤销）
行为：写 `manual_verdict_by/at`（撤销时置 NULL）；**重算批次三档计数**。响应 data：更新后结果对象。

## 10. 实现注意

1. **路由注册顺序**：`/talents/search`、`/talents/duplicates` 必须在 `/talents/{id}` 之前注册。
2. **进度可见**：批次每完成一人即写 progress + heartbeat；前端 2s 轮询。
3. **HTTP 路径禁 LLM（Embedding 有例外，决策 D-B）**：任何同步接口**不得调用 LLM**；**允许**调用 Embedding/Milvus 的三处是 `GET /talents/search`（查询路径，有短期缓存，按 D-10 口径计量）、`PATCH /talents/{id}` 与 duplicates `merge`/`restore`/`revector`（单次写入，受 `VECTOR_SYNC_TIMEOUT` 5s 约束，v1.4）。除此之外所有 AI 调用只在 TaskRunner。
4. **单进程约束**：一期 `--workers 1`（多进程会重复扫描任务），写入运行手册。
5. **DELETE 幂等**：`DELETE /talents/{id}` 重复删除统一 404；`DELETE /resumes/queue/{id}` 是**软取消**（置 `cancelled`），对已 `cancelled` 的任务再删也返回 404；前端全部二次确认，并在确认框提示「可用 requeue / restore 恢复」。
6. **计数一致**：批次 `done` / 改判后均按结果表重算计数；`total` 取 `resolved_ids` 快照长度，与 `progress` 不等时以 `processed`/`skipped_deleted` 解释差额。
7. **筛选路径不得触碰向量依赖**：`screen_worker` 调 `match_engine` 时传 `use_vector=False`（《算法与判定规则》§4.0）。这是验收第 12 条「Milvus 未启动时筛选不受影响」能成立的**唯一前提**，代码评审必查。
8. **解析重试必须断点续跑**：`retry` 保留 `stage`；worker 按 `stage` + `parsed_resumes.talent_profile_id` 跳过已完成步骤；查重时**排除本 parsed_resume 已指向的画像**；建画像与回填 `talent_profile_id` 同事务（《数据库设计》§4.2.1）。
9. **`duplicate_pending` 只能由 resolve 流转**：runner 不扫描该状态；`merge` 必须把任务写成 `success` 并填 `profiled_at/finished_at`，`keep` 必须把任务写成 `pending + stage='profile'` 交回 runner，**不允许**任务永久停在 `duplicate_pending`。

## 附录 B：筛选/匹配范围（scope）语义

| scope.type | 语义 |
|---|---|
| `all_unscreened` | 该 `job_profile_id` 在 `screen_results` 中无任何记录的人才（不重复筛） |
| `upload_batch` | `resume_files.upload_batch_id` 匹配、解析成功且已有画像 |
| `resume_file_ids` | 显式指定文件，解析成功且已有画像 |
| `all` | 全部未软删除、已有画像的人才（复筛） |
| `filter`（仅匹配） | 按 degree/min_years/tags（talent_tags）圈定 |

**圈定只在创建批次的那一刻发生（决策 D-D）**：上表语义用于 `POST /*/batches` 的同步阶段，解析出的 `talent_profile_id` 清单写入 `scope_json.resolved_ids`（匹配为 `talent_scope_json.resolved_ids`），`total = len(resolved_ids)`。此后 worker 执行、心跳恢复、retry **一律只读该清单**，不再按上表重新查询。所以：

- 创建时仍在解析（`pending`/`running`/`duplicate_pending`）的 `upload_batch` 简历**不会**进入本批；如需纳入，等其 `success` 后**另建批次**。
- retry 前新增的画像**不会**被补进旧批次。
- 快照内画像被软删：已写结果行保留（姓名 + "已删除"标记），未执行的成员跳过不写行，计入 `skipped_deleted`。
