## Layer 1 · 开发规范（开发前必读，固定不变）

### 1.1 流程规范

1. **每跑通一个功能模块都要先测试，测试通过再开发下一个功能**。测试分三级（见 §1.2），三级全过才能把任务标记为 ✅ 已完成
2. **先写公共部分的代码，之后要修改公共部分的代码需要我确认才能修改**。公共部分边界见 §1.3
3. **每次开发都需要先读这份日志文档**（包括 Layer 0 快速索引、Layer 1 规范、Layer 3 当前任务进度）
4. **遇到阻塞、新决策、计划外需求时先问我**，不要自己定；日志里记 `⏳ 待决策`
5. **不做超出当前任务范围的改动**：比如做 T-12 时顺手改了 T-16 才用到的 schema，要在日志里说明并标记为"超前改动"
6. **每完成一个任务在 Layer 3 登记**：状态 + 实际做法（如计划有变）+ 测试结果 + 遇到的坑。不登记不算完成

### 1.2 测试三级定义

| 级别 | 内容 | 通过标准 | 何时跑 |
|---|---|---|---|
| L1 单元测试 | 函数级，mock LLM/DB，不触真实外部服务 | 全部用例绿 | 每个原子任务写完立即跑 |
| L2 集成测试 | 模块级（如 parse_service 调用 llm_client），可用假 LLM server | 链路全通，假数据可产出正确结构化输出 | B1 起每个模块完成后跑 |
| L3 真实集成测试 | 真实 LLM + 真实 Milvus + 真实 MySQL 端到端 | 全链路从上传到画像/筛选/匹配无失败，真实数据正确 | B6 联调阶段集中跑，不要求开发阶段每个任务都跑 |

> **原因**：真实 LLM 调用慢（单条几秒到几十秒）、耗 token、开发阶段频繁跑会拖进度。开发时先保证 L1+L2 绿，B6 再开 L3 集中验证。如果某任务必须 L3 才能验收（比如向量 upsert），日志里会注明。

  - **DOCX（python-docx）**：正文按 `w:p` / `w:tbl` 的**真实顺序**输出（不是段落全在前、表格全在后）；表格一行一条记录、单元格用 `\t` 分隔、嵌套表最多再取一层；页眉/页脚按内容去重（多节常重复同一句）；合并单元格导致的相邻重复内容去掉

  - **不伪造配置键**：运行配置 v1.3 没有 `TEXT_MAX_CHARS`，因此用常量 `DEFAULT_TEXT_MAX_CHARS = 15000`；将来要可配，先在运行配置登记再改成读 `settings`

  ② **按字符（码点）截断而非字节**：与"≤15000 字符"口径一致；截断点可能落在句子中间，**不做按段落回退**（回退会让实际长度忽长忽短，反而难以预测）

  - **失败兜底**：handler 未捕获的异常由 runner 置 `failed` + `error="任务执行异常：..."` + `finished_at`，不会永远 `running`；业务失败仍由 worker 自己写 `failed(stage=...)`
  - **优雅停止**：`stop()` 置停止事件 → join 主循环 → 等在跑 future 至 `TASK_SHUTDOWN_TIMEOUT`（30s）→ 超时任务回置 `pending`（保留断点）→ 关池；线程无法强杀，进程退出即结束
